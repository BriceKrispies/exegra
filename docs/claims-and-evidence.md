# Claims and evidence

The rule of `src/core/claims.js`: never confuse *declared* with *true*. A claim is a statement with an explicit evaluation method. A result says what was checked, and the status is derived from what was checked, not from the claim existing.

## Claims

```jsonc
{
  "id": "no-direct-client-to-database",
  "kind": "structural",
  "statement": "The web client has no direct relationship to the persistent game database.",
  "subjects": ["web-client", "game-database"],
  "assumptions": [],
  "evaluate": { "method": "no-relationship", "from": "web-client", "to": "game-database", "transitive": false }
}
```

`kind` is `structural`, `invariant`, `temporal`, `measured` or `requirement`. A `requirement` is a statement whose verification is carried out outside Exegra (see [External verification methods](#external-verification-methods)). `evaluate.method` must be listed in `claim-methods.js` for that kind, or be a method the specification declares itself, and may carry only that method's parameters; otherwise validation reports `claim.method.kind` or `claim.param.unknown`. An unknown method is only a warning (`claim.method.unsupported`) and the claim stays not evaluated. `assumptions` reference `assumption` entities, conditions accepted without evidence; they are listed in the result and are never checked.

## Requirement realisation

A requirement may state how the system comes to satisfy it, in `realisation`:

- `construction`: generated code guarantees it. Some claim must name the requirement in `models`, or the requirement names at least one cross-cutting construct (a policy, validation, retention, quota, retry or audit) in `realisedBy`; otherwise validation reports `requirement.construction-unmodelled`, always, because a guarantee by construction that neither a check over the model restates nor a construct generates guarantees nothing. See [Model and format](model-and-format.md#cross-cutting-constructs).
- `checked`: hand-written code satisfies it and tests check it, through Concordance.
- `operational`: it is measured on a running deployment (budgets, deployment and operations requirements); no code satisfies it by itself.

When the specification sets `system.generation`, every requirement must state `realisation` (`ready.requirement-realisation-missing`; see [Model and format](model-and-format.md#types-contract-details-and-generation-readiness)). The property does not change how a claim is evaluated.

## Fault models

A claim may name a fault model (`faultModel`, an entity of kind `faultModel`, see [model-and-format.md](model-and-format.md#fault-models-and-sources)): the environment and the failure modes it is evaluated under. The result's `scope` then begins with "Under fault model <name> (<n> failure modes; bounds: ...)." followed by the scope the method states, for every method, `external-evidence` and externally verified methods included. For the trace methods (`state-invariant`, `precedes`, `eventually`, `never`) the explanation also says how many of the model's failure modes the listed scenarios inject (through the `realises` of their faults); the others were not exercised. Naming a fault model does not make a claim stronger: it states what the result is scoped to. Failures outside the model are not covered, and the model says where that boundary is. An invariant, temporal or measured claim with no fault model, in a specification that declares one, is reported as the gap `gap.no-fault-model`.

## Methods

| Method | Kinds | Establishes |
|---|---|---|
| `no-relationship` | structural | No relationship (optionally no multi-hop path, `transitive`) from any `from` component to any `to` component. |
| `reachable` | structural | Every `from` component reaches some `to` component along a path of at least one relationship; being a member of the target set is not reaching it. |
| `only-via` | structural | Every directed path from `from` to `to` passes through `via`. |
| `has-port` | structural | Every selected component has a port matching `direction`, `contract`, `name`. |
| `property-defined` | structural | Every selected component has a non-empty value for a property (dot path). Presence only, not correctness. |
| `acyclic` | structural | The graph of the given relationship kinds or dependency classes (default: kinds flagged `dependency`, which are the classes `static` and `runtime`) has no cycle. |
| `data-model` | structural | The listed data rules (`rules`, default all six; optionally only the `records` named and their copies) find nothing on the model's records and copies. Violated with the findings as counterexample; inconclusive when a listed rule has nothing to check. See [model-and-format.md](model-and-format.md#data-model). |
| `state-invariant` | invariant | An expression holds in the initial configuration and after every step of each listed scenario. |
| `precedes` | temporal | In each listed scenario, every occurrence of `then` has an earlier `first`. |
| `eventually` | temporal | In each listed scenario, `occurs` happens, or `expr` holds in the final configuration. |
| `never` | temporal | In each listed scenario, `occurs` never happens. |
| `lean-theorem` | structural, invariant, temporal, requirement | A theorem of the Lean core (`theorem`, fully qualified) states the claim, and Lean checks it: the constant exists and is a theorem, the kernel accepts its proof again (re-added under a fresh name), it depends on no axiom beyond `propext`, `Classical.choice` and `Quot.sound`, and each implementation constant in `about` is a definition that occurs in its statement. See [Lean theorems](#lean-theorems). |
| `implementation-language` | structural | Every selected implemented component (`select`, minus `exclude` taken exactly) records `implementation.language` equal to `language`. Violated with the components that are not, by language, with progress and the task named in `plannedBy`. |
| `abstraction-well-formed` | structural | Every listed hierarchy (`hierarchies`, default all, `logical` included) is laminar and acyclic with every module element under one element, and every listed cut (`cuts`, default all) is an antichain covering every element whose abstraction map sends each element at or below it to exactly one block (docs/model-and-format.md, "Elements, hierarchies, facets and cuts"). Violated with the offending elements. |
| `abstraction-invariants` | structural | The derived models of the listed cuts (`cuts`, default every declared cut), with kinds as declared and coarsened to the top kinds, satisfy the listed invariants (`invariants`, default all): `witness-completeness` (I1), `boundary-accounting` (I2), `recoverability` (I3), `interfaces-from-boundaries` (I4), `functoriality` over every comparable pair of the listed cuts (I5), `kind-preservation` (I6) and `determinism` (I7). Each is recomputed from the relationships (`src/core/abstraction.js`, `abstractionInvariants`). See [Claims stated at a cut](#claims-stated-at-a-cut). |
| `refines` | temporal | The implementation behavior `behavior` refines the model behavior it names in `refines`, through its `refinement` mapping, on the traces of its scenarios. See [Refinement](#refinement). |
| `external-evidence` | any | Nothing is evaluated. The status comes only from attached evidence. |

The four graph methods (`no-relationship`, `reachable`, `only-via`, `acyclic`) select the relationships they follow by `kinds` (relationship kind names), by `classes` (dependency classes: `static`, `runtime` or `none`, see [Interaction kinds](model-and-format.md#interaction-kinds)), and by `where`. A relationship must pass every filter that is given, so `kinds` and `classes` together are an intersection. `{"method": "acyclic", "within": "semantic-core", "classes": ["static"]}` checks only what the core's components name in their own code; `"classes": ["static", "runtime"]` is exactly the dependency kinds. A legacy kind has the class of the kind it behaves as (`calls` is `runtime`). An unknown class, like an unknown kind, is `inconclusive` rather than a vacuous pass, and the result's `scope` says "of class ..." when a class filter applied. A claim that states neither keeps its default.

A **selector** picks components: an id, an array of ids, or an object (`ids`, `category`, `kind`, `tag`, `facet`, `trustZone`, `within`, `outside`, `except`, `all`; all present fields must match; `facet` names a declared facet or a tag, docs/model-and-format.md#elements-hierarchies-facets-and-cuts). Components nested in a selected subsystem are selected. `outside: X` selects the complement of X: every component that is not X, not inside X and not an ancestor of X, so an element added later is covered without being listed. `except: [{"id": ..., "reason": ...}]` removes components (and what they contain) from the selection; each exception needs a reason, so nothing is left out silently.

### Claims stated at a cut

The four graph methods take `cut`, a declared cut (WG-5694). The claim is then evaluated on the derived model of that cut (`src/core/abstraction.js`, `node cli/exegra.js derive --cut <id>`): its selectors pick blocks, its graph is the lifted interactions, each carrying every relationship it stands for. The verdict reaches the components inside the blocks only through the transfer rules of the multiscale audit (docs/assessment/2026-11-27/multiscale.md, section 3.3):

- **Absence transfers exactly.** No derived interaction (no path of them) between two blocks means no relationship (no chain of them) between any of their members, so a verified `no-relationship` at a cut holds for every member.
- **Presence transfers upward.** A derived interaction is witnessed by relationships between members; a direct violation names them.
- **A coarse path is a may-path.** It can join a relationship into a block with another out of it that nothing inside the block connects (a spurious path). `reachable` is verified, and a transitive `no-relationship` or `only-via` violated, only when a chain of relationships between members witnesses the coarse path; otherwise the claim is `inconclusive`, and the explanation says may-reachable.
- **Acyclicity is a statement about blocks.** `acyclic` at a cut is violated by a cycle of blocks even when no chain of relationships closes a cycle, and verified means every cycle among the relationships lies inside one block.
- **Not expressible at this level.** A claim whose selector names an element hidden inside a block of its cut, or picks some but not all of the components a block holds, is `inconclusive` with the diagnostic `claim.not-expressible`; it is never quietly re-scoped to the leaves. A block named by id in a selector stands for every component it holds at the cut, in whichever hierarchy the cut is of (the blocks of an accepted decomposition, a runtime placement), not only the components the logical hierarchy nests in it.

`core-independent-of-ui` is stated this way: at `l1`, from `semantic-core` to `{"outside": "semantic-core", "except": [...]}`, with the JSONC parser library and the JavaScript runtime excepted with their reasons.

Every result of a model-decided method also records its **footprint** (`result.footprint`, `src/core/footprints.js`): the entities it read, the kinds of entity it read whole, whether selector resolution mattered, a query over relationships (the kinds, classes and `where` it followed) and, at a cut, the abstraction structure. `claimsToRecompute(results, before, after, affected)` gives the claims an edit's affected set can change; the others keep their results. Footprints concern the model a result read; whether recorded evidence describes the current files stays the business of tree stamps (`freshness`). A **matcher** is `{ "event": id }` or `{ "transition": id }`.

### Negatives

Every trace method (`state-invariant`, `precedes`, `eventually`, `never`) takes `negatives`: runs that must **violate** the claim. A negative is one of the claim's own scenarios run with extra faults, `{ "scenario": id, "faults": [ids], "note"?: text }`; the run uses the scenario's own faults plus these. Because it is the same script with something taken away, a violation shows that the protection the claim is about is what makes it hold.

```jsonc
"evaluate": { "method": "state-invariant", "scenarios": ["edit-with-disk-conflict"],
              "expr": "workspace-flow.conflict => workspace-flow.persistedRevision == 1",
              "negatives": [ { "scenario": "edit-with-disk-conflict", "faults": ["conflict-overwrites"] } ] }
```

The fault usually enables a `faultOnly` transition that models a defect the system must not have (here: the workspace writes despite the conflict), or drops, delays, injects or disables something. The validator reports a negative whose scenario is not one of the claim's (`claim.negative.scenario`), whose `faults` is missing or empty or names a fault its scenario already activates (`claim.negative.faults`), or that has another field (`claim.negative.unknown`); an undeclared fault is a reference error. Renaming a scenario or fault rewrites the negatives that name it.

Each result of a trace claim lists its negatives under `negatives`: `scenario`, `faults`, `violated`, the run's `outcome`, the `stepIndex` of the violation and an `explanation`.

## Refinement

A specification can hold two layers of state machines: abstract **model** behaviors, used for checking, and detailed **implementation** behaviors (`level: "implementation"`), from which code could later be generated. An implementation behavior I says which model behavior A it refines and how its configurations map onto A's:

```jsonc
{ "id": "lease-impl", "level": "implementation", "refines": "lease-model",
  "refinement": {
    "states":      { "li-free": "lm-free", "li-held": "lm-held", "li-renewing": "lm-held" },
    "variables":   { "holder": "owner", "epoch": "gen" },
    "transitions": { "li-acquire": "lm-acquire", "li-renew": null, "li-renewed": null, "li-release": "lm-release" } } }
```

`states` maps every state of I to a state of A; `variables` gives, for every variable of A, an expression of the expression language (`src/core/expr.js`) over I's variables (bare names only); `transitions` maps every transition of I to a transition of A or to `null`, a **stutter**: a step of I that A does not see. The ids inside the mapping are plain strings, not references, so renaming a state or transition does not rewrite them (validation then reports the stale name).

`timeScale` (optional, default 1) is the number of implementation time units per model tick, for a model that counts in ticks refined by an implementation that counts in, say, milliseconds (`"timeScale": 60000` for one-minute ticks). It changes two things and nothing else: wherever the check evaluates a model guard or effect, `time` is the trace time divided by `timeScale`; and a model timer's numeric `after` is multiplied by `timeScale` before it is compared with the implementation's timer. The division is one IEEE 754 double division, as every Exegra number is a double (`src/core/expr.js`, `formal/Exegra/Number.lean`), and model expressions then evaluate in doubles as the engine's do. It is exact whenever the trace time is a multiple of `timeScale` (the quotient is an integer below 2^53), so a boundary that must be decided exactly, such as `time - issuedAt <= 15` at the 15th tick, should fall on such an instant; between multiples the quotient is correctly rounded, not a rational. The mapping expressions, the implementation's own variables and other behaviors read by model expressions are not scaled: a mapping converts implementation quantities itself (for example `"issuedAt": "(expiresAt - 900000) / 60000"`). A `timeScale` that is not a positive number is the error `refinement.time-scale`; `refinement` without `refines` is already `behavior.refinement-without-refines`.

Validation refuses, as errors: a `refines` that names something other than a behavior (`ref.kind`, `ref.unresolved`); a `refines` on a model-level machine, whose `level` is absent or `model` (`behavior.refines-model-level`); refining a behavior that itself refines, since refinement has one level (`behavior.refines-chain`); `refines` without `refinement` (`behavior.refinement-missing`) and the reverse (`behavior.refinement-without-refines`); a key or value that is not a state or transition of the right side, or a mapping expression that reads anything but I's variables (`refinement.unknown-state`, `refinement.unknown-transition`, `refinement.unknown-variable`; a mapping that does not parse is `refinement.expr`); and a state or transition of I, or a variable of A, missing from the mapping (`refinement.unmapped-state`, `refinement.unmapped-transition`, `refinement.unmapped-variable`). A `refines` claim must name one behavior that declares `refines`, and each scenario it lists must run that behavior (`claim.param.value`).

**The check.** `{"method": "refines", "behavior": "<I>", "scenarios"?: [ids]}`, implemented in `src/core/refinement.js`, is a forward simulation with the mapping, evaluated on traces. Write `map(c)` for the model configuration of an I machine `c`: the state `states[c.state]` and, for each variable `v` of A, the value of `variables[v]` on the variables of `c`. The engine runs each scenario (the listed ones, or by default every scenario whose `behaviors` include I) with its own faults, exactly as the trace methods run theirs, and on each trace:

1. **Initial.** For every machine of I in the initial configuration (and for a keyed instance, the configuration it is created with), `map(c).state` is A's `initial`, and each mapped variable equals the `initial` of A's variable.
2. **Steps.** For every transition `t` that a machine of I fires, from `c` (its configuration before the step) to `c'` (after it):
   - if `transitions[t]` is `null`: `map(c).state = map(c').state`, every mapped variable is unchanged, and `t` emits nothing (strict: a stutter has no observable output);
   - otherwise, with `a = transitions[t]`: `a.from = map(c).state`; `a.on` is the delivered event (`t.on`); `a.to = map(c').state`; `a` is not `faultOnly`; and `a` is the transition **A itself would fire**: no transition of A declared before `a` with the same `from` and `on` has a guard that holds, and `a`'s guard holds. Guards and effects of A are evaluated on the mapped variables of `c`, with the step's event payload (`event.<field>`) and time (`time`, the trace time divided by `timeScale`). Applying `a`'s effects in order (a later effect reads an earlier `set`) to the mapped variables of `c` gives exactly the mapped variables of `c'`. The events `t` emits are the events `a` emits, by event id, in the same order and number; for each payload field that `a`'s emit sets, `t`'s emitted payload has that field with a structurally equal value; fields only `t` sets are implementation detail and are not compared. `cancel` effects are not compared; how a delayed emit is compared is under Timers below.
   - **Timers.** A trace step lists the entries a transition queued in `emitted`, emits and timers alike, in effect order. The check tells them apart by the transition's own effects: each `emit` and each `timer` effect queued exactly one entry, in declaration order (a `cancel` queued none); a transition whose effects cannot be matched this way (a fan-out emit, an emit over a link, a resource effect, or a count or event that differs) makes the result inconclusive. An emit is *delayed* when it has an `after` other than 0. A delayed emit and a timer are different things and neither realises the other: a delayed emit goes to its receivers `after` the step, a timer fires its event back at its own machine. So the implementation's emits, delayed or not, are compared with the model's emits, delayed or not, in effect order (reason `emits`): the same events, in order and number, with the payload fields the model sets equal; each emit delayed exactly when the model's is (an emit at once for a delayed one, or the reverse, is a violation); and where the model's `after` is a number, the implementation's emit is delivered at the step's time plus that number times `timeScale` (a duration or a distribution is not compared). A model's `{emit, after}` is therefore realised only by an implementation `{emit, after}` of the same event at the scaled delay; an implementation timer for that event, even with the model's delay, leaves the model's emit unmade and is violated with reason `emits`. A timer the implementation sets is compared only when the model transition sets timers: then the timers must emit the same events, in order and number, with the payload fields the model sets equal, and where the model's `after` is a number the implementation's timer must fire at the step's time plus that number times `timeScale` (reason `timers`). When the model transition sets no timer, the implementation's timers are internal to it and are not compared, and a stutter may set timers but emits nothing, delayed or not. A timer's later firing is a delivery like any other: the transition the implementation fires on it is checked as its own step, against the model transition the mapping names (which is triggered by the same event) or as a stutter.
   - **Other behaviors.** A model guard or effect may read another behavior, `<B>.state` or `<B>.<variable>`, as in the engine. It is read from the same trace: from the machine that ran under the id `B` in the run, or, when none did, from the one machine of the run whose behavior refines `B`, through that behavior's refinement mapping (its `states` for `state`, its `variables` expression for a variable). A guard reads the configuration before the step. An effect reads it as the engine's effects do: the configuration after the step for a machine that fired earlier in the same step (scenario order), and the one before the step otherwise. `<A>.state` and `<A>.<variable>` of the model itself read the mapped state and variables. A behavior with several instances in the run, one that no machine of the run is or refines, one that two machines refine, and a three-part reference (an aggregate) make the result inconclusive.
   - **Instances.** A format-2 trace names the instance of every fired entry, `0` for a behavior without `instances`, while that behavior's machine key is its bare id; the check takes the machine `<I>#<instance>` when the configuration has one and the bare id otherwise.
   - **Ignored inputs** (WG-5685). When the engine records that a machine of I took no transition on the delivered event (`ignored`, reason other than `disabled`; in a trace without `ignored`, when I fired nothing in the step), A must ignore it too: no transition of A from `map(c).state` on that event, not `faultOnly`, may have a guard that holds on the mapped variables. Otherwise the check fails with reason `ignored-input` at that step, the counterexample naming the model transition A would take. An implementation that silently refuses an input its model handles (`docs/assessment/2026-11-26/demos/refines-ignore.mjs`: `li-renewing` ignores `release`) is refused, not verified.
3. **Verdict.**
   - **violated** at the first failing check, with `counterexample` carrying the `scenario`, the `stepIndex` (`-1` for the initial configuration), a `reason` (`initial-state`, `initial-variables`, `unmapped-transition`, `model-from`, `model-event`, `model-to`, `model-fault-only`, `model-not-chosen`, `model-guard-false`, `ignored-input`, `post-variables`, `emits`, `timers`, `stutter-state`, `stutter-variables`, `stutter-emits`, `mapping-error`, `model-expression-error`) and `trace`: the steps of I checked so far in that scenario, each `{scenario, stepIndex, machine, event, transition, implFrom, implTo, model, modelFrom, modelTo, ok}`, the last being the failing step with `ok: false`. A mapping expression, or a model guard or effect, that fails to evaluate on a reached configuration (an error of the expression language) is a violation: the mapping is not a function there.
   - **inconclusive** when a scenario cannot be run or ends in an error (the steps before it were checked, but the run did not complete); when a listed scenario does not run I; when a model expression reads something the check does not resolve (see Other behaviors; an aggregate; `instance`), a model transition has a resource effect or a sampled `set`, or an implementation transition's queued entries cannot be told apart (see Timers); when no scenario runs I; and when I fired no transition, or only stutters, in every trace (vacuity is not verification: nothing of A was matched).
   - **verified** otherwise: every initial configuration and every step passed, and at least one step matched a model transition. A run cut off at its step limit is reported as the trace methods report it: the steps it executed were checked, and the scope and explanation say that later steps were not run.

**Every delivery order** (WG-4852, WG-5685). After the engine's trace of a scenario passes, `src/core/refinement-explore.js` explores the other executions of the same input: from the initial configuration it delivers, at each configuration, each pending entry of minimal time (a scenario step or an event a behavior emitted), with the engine step of `src/core/replay.js`, and checks every step it reaches as above, exploring each configuration once. A failing step the engine's order does not reach makes the claim **violated**; the counterexample carries the delivery `order` and `explored: true`. The exploration is **inconclusive**, never verified, when it reaches its cap of configurations (5000) or the scenario's step limit with entries pending, or when the scenario has what it does not enumerate: faults (their masks), sampled delays or values (their draws), timer cancellations, counted or keyed instances, resources, workloads or links.

**What a verified result establishes**: on the listed scenarios' inputs, in the engine's trace and in every execution that delivers simultaneous entries in another order, every step of I maps under the mapping to the step A takes from the mapped configuration, emitted events included. **What it does not establish**: refinement on other inputs or under faults and draws (a scenario with them is inconclusive); anything after a step limit; that A's environment is the one the other behaviors' models describe (another behavior is read from whatever machine ran under its id or refines it, as it ran); and anything about generated or hand-written code. A `refines` claim takes no `negatives`: unlike a trace property it compares each step with a second machine, and the violated cases of `tests/core/refinement.test.js` show each part of the check failing. The check is JavaScript in the verdict-kernel component `claim-evaluator`, not yet ported to Lean, so `core-logic-in-lean` lists it with that component.

## Composition claims

The claim methods of behavioural composition ([composition.md](composition.md)) are decided by the model, on the Lean engine's runs, with hiding and the comparison of runs decided in Lean:

| Method | Verified when |
|---|---|
| `refines-composition` | A declared abstraction (`behavior`, which declares `abstracts`) gives the same boundary trace as its members (or, with `finest`, its finest members) in each listed scenario, with strength conservative; each negative (a listed scenario with extra faults, applied at whichever level has the transition) breaks it. Violated with the first boundary counterexample. |
| `environment-assumed` | In each listed scenario every delivery to an omitted element is covered by an environment assumption; each negative `{scenario, without: [elements]}` reports one once those assumptions are dropped. |
| `order-independent` | No verdict of the listed scenarios (default: all), or of their claims' negative runs, changes when their behaviours are listed reversed or rotated. |
| `transfers` | The preservation rules applied to `claim` and `abstraction` give `expect` (`transferred` or `not-transferred`). |
| `alternatives-reconciled` | The listed elements (default: all) have no alternative machines. |
| `interfaces-closed` | Every event belongs to an interface, every cross-element read is exported by a declared interface it crosses, and declared interfaces list their members' boundary events. |

Like a `refines` claim, a refinement verified this way is a check of the scenarios' runs, not of every interleaving.

## Statuses

Every status is decided in Lean (`formal/Exegra/Verdict.lean`). The claim evaluator runs the checks Exegra can run over its model and reads the recorded results; each becomes a **fact** in the Lean schema (`kind`, `subject`, `target`: a part of the claim or an assumption, `stamps`: recorded and current, `outcome`: pass, fail, not-run or undecided), built by `src/core/facts.js`, and the Lean function `claims.status` decides the status of every claim from its facts. A fact that does not decode is refused and reported as `claim.fact-refused`. The status is a tuple, carried by every result as `verdict`:

- **strength**: `refuted` < {`undecided`, `asserted`} < `checkedOnInstances` < `exploredToBound` < `proved`, where `undecided` and `asserted` are incomparable. A fresh passing fact gives at most what its kind can establish: a test, a trace check, a statistical test or an external tool's outcome `checkedOnInstances`, a structural check over the whole model `exploredToBound`, a Lean theorem `proved`, a document `asserted`. A failing fact refutes; a part with no usable fact is `undecided`. An evidence-based claim is the conjunction of one part per piece of test evidence (documents back every part) and takes the meet of its parts, so one untested part leaves it undecided.
- **subject**: `model` (the checks Exegra runs over its model), `implementation` (evidence-based and `lean-theorem` claims, a `measured` claim included: its load test or benchmark runs the implementation) or `reality` (a requirement realised operationally). Strength never carries across subjects: a passing test about the implementation does not raise a claim about the model.
- **open assumptions**: the assumptions no fresh fact discharges. A claim one of whose assumptions is refuted (an import scan, a recorded test) is `undecided`, not refuted: it may still hold.
- **freshness**: `fresh`, `stale` or `unverifiable` (below). Only fresh facts give strength.

A status is **shown established** only when it is `proved`, fresh and has no open assumption (`established` in `verdict`; the capability matrix lists only these). The word a status is shown with (`status`) is decided by Lean too:

| Status | Meaning |
|---|---|
| `proved` | A `lean-theorem` claim: the Lean kernel checked a theorem that states it, with only the standard axioms, about the named Lean definitions. It covers every input, not a list of scenarios. It is about the code that runs to the extent the trusted base holds (the claim's assumptions: the Lean compiler and runtime, emscripten, the JS glue, the WebAssembly engine). |
| `verified` | An evaluator checked the model and found no counterexample, within the stated scope. A trace claim also needs a declared negative, and every one must violate it. |
| `supported` | No evaluation by Exegra; fresh executed evidence (tests, an external tool) checked the implementation on instances, every part of the claim included. |
| `model-holds` | A metric claim's statistical tests hold in the model on every scenario, every negative fails and every control negative holds. |
| `asserted` | Only author-entered evidence (a document, a review) backs the claim: written down, not established by anything Exegra checked. |
| `violated` | A counterexample was found, or recorded or declared evidence contradicts the claim. |
| `inconclusive` | Something was checked, but not enough to decide. |
| `not-evaluated` | Nothing was checked: no method, an unsupported method, or `external-evidence` with no evidence; or the facts the status would rest on are **stale** (recorded for other files than the current ones, below), and the explanation starts with "Stale:". |

The rules are theorems of `formal/Exegra/Verdict.lean`, each checked by `lake build Exegra` with its axioms pinned: a conjunction takes the meet of its parts (`status_conj`), a contradicting fact never raises a status (`contradict_lowers`), staleness never raises it (`stale_never_raises`), a refuted assumption leaves a claim undecided (`refuted_assumption_undecided`), established means proved, fresh and no open assumption (`established_iff`), the strength never exceeds what the kinds of the fresh facts used can establish (`strength_le_kind`), and a regression is a removal or a move that is not upward in the status order (`regression_iff`). `admit` and `verify` decide regressions with `verdict.isRegression`.

Rules that keep the statuses honest:

- **Vacuity is not verification.** A selector that selects nothing, a graph with no relationship of the requested kinds, an unknown relationship kind (a misspelling would pass vacuously), a `precedes` whose `then` never occurs, and a claim that lists no scenario are all `inconclusive`. So are the trace cases that would otherwise pass for want of anything to check: a `state-invariant` that is an implication whose antecedent is never true in a configuration reached by a step of any listed trace, or whose consequent names no state or variable (a constant), a `precedes` whose occurrences are all deliveries from the scenario script (an ordering the script itself dictates; a transition, or an event a transition emitted, must be one of its witnesses), a `state-invariant` over traces that all have zero steps, and a `never` about an event or transition that cannot occur in the scenario (a transition of a behavior the scenario does not run; an event that no transition of its behaviors triggers or emits and that is neither a step event nor injected by a fault).
- **A trace check that cannot fail is not verified.** A trace claim that holds on its scenarios is `verified` only when it declares at least one negative and every negative definitely violates it. With no negative it is `inconclusive` ("declares no negative, so nothing shows this check can fail"); so it is when a negative holds, ends in an error, or is cut off at its step limit before an expected occurrence (an absence in an unfinished run is not a violation). A claim violated on its own scenarios stays `violated`; negatives never soften it.
- **A result says what its verdict rests on.** When the engine took the first of two enabled, unguarded transitions of one behavior on the same event and state because it was declared first, the scope names the pair ("Declaration order decided which transition fired") and says swapping them would change the traces; `validate` warns about such a pair (`transition.order-decides`). A later transition with a guard is not examined for this: whether its guard held is not evaluated. A `never` over an occurrence that only `faultOnly` transitions can produce says so in its scope when no listed scenario enables them: it holds for runs without that fault, and for runs with it only as far as a negative exercises it. An implication that is verified counts as exercised when its antecedent was true after some step; whether its consequent could have been false there is shown only by its negatives.
- **A requirement shows the checks over the behavior model that restate it.** A claim may name a requirement in a `models` property (a vocabulary property of type `ref` to `claim`, as the Strata specification declares). The requirement's result then carries `modelledBy`, the claims that name it with their statuses (listed by `exegra claims`, and in the inspector under "Checked over the behavior model by"). It is information: the requirement's own status does not change. A `models` value that is not a requirement (a claim of kind `requirement`) is the validation error `claim.models-not-requirement`.
- **An expression that cannot be evaluated is a violation.** A `state-invariant` whose expression cannot be evaluated in a configuration (a division by zero, an unknown reference, a value that is not a Boolean), or an `eventually` whose expression cannot be evaluated in the final configuration, is `violated`, as `exegra prove` decides it: the live view evaluates claim expressions, matches occurrences and runs the `precedes` monitor with the Lean functions `exegra prove` uses (`claims.exprOnConfigs`, `claims.matcherHits`, `claims.formViolation` over `claimTruth`, `Matcher.hit` and `Form.step` of `formal/Exegra/ProveB.lean`). A `liveness` claim is never decided from a trace: it stays `not-evaluated` in the live view and is decided by `exegra prove` (docs/simulation.md, Liveness).
- **Trace methods check only the listed scenario traces**, run with the scenario's own faults. Every result's `scope` says so: "This is a check of these traces, not of all possible executions." A scenario that ends in an error or hits its step limit before an expected occurrence cannot establish an absence, and makes the claim `inconclusive`.
- **Discharge is not circular.** A claim that `discharges` an assumption establishes it for the claims that cite it. The discharge graph (an assumption depends on the claims that discharge it, a claim on the assumptions it cites) must have no cycle: validation refuses one with the error `assumption.discharge-cycle`, naming its nodes (`tests/fixtures/discharge-cycle`). Over an acyclic graph, every guarantee that holds under its assumptions holds outright (`Exegra.Core.discharge_sound`, formal/Exegra/Core/Contract.lean); with a cycle, two claims could each rest on the other.
- **Evidence can only make a model-evaluated claim worse.** A `verified` result with contradicting evidence (declared `supports: false`, or a recorded `fail`) becomes `violated`.
- **A stale fact never makes a claim positive.** A recorded result, an external tool's outcome or a Lean theorem check recorded for other files than the current ones is stale ([Freshness](#freshness-of-recorded-facts)): a stale pass establishes nothing and a stale failure still counts.
- **Every result carries a scope, an explanation, the assumptions, the entities involved** and, when violated, a counterexample (a path, a relationship set, or scenario and step). Results are stamped with the semantic hash they were evaluated at.
- **Live checks in the simulator** (`checkTrace`) apply only to claims that list the loaded scenario, and distinguish *undecided* (`pending`) from *violated*: an `eventually` still waiting in an unfinished run is undecided, and so is a vacuous implication on a finished trace. See [simulation.md](simulation.md).

## External verification methods

A specification's `vocabulary.verificationMethods` declares methods that Exegra does not run, for example a property test, a scenario run or a conformance table carried out by another tool ([model-and-format.md](model-and-format.md#meta-model-and-vocabulary)). A claim whose `evaluate.method` names one has no other parameters, gets the evaluator `external:<method>`, and is treated like an `external-evidence` claim: no evidence gives `not-evaluated`, contradicting evidence gives `violated`, a recorded pass or an author-entered item gives `supported`, and untested `test` evidence gives `inconclusive`. It is never `verified`: the result's scope says "Exegra ran nothing" and names the method. The claim kind `requirement` exists for this, and a specification converted from Markdown (a linked project) uses it for every requirement it holds, none of which has evidence, so all are `not-evaluated` ([importing-markdown.md](importing-markdown.md)). `tests/core/vocabulary.test.js` checks that such a claim is never reported as verified by Exegra.

## Lean theorems

A `lean-theorem` claim names a theorem of the Lean core and the implementation constants it must be about (at least one: a claim with no `about` is refused):

```jsonc
"evaluate": { "method": "lean-theorem", "theorem": "Exegra.runInput_terminates", "about": ["Exegra.runInput"] }
```

Lean does the checking (`tools/lean-theorems.js`, through `lake env lean` in `formal/` on the built library) and reports facts per theorem: whether it exists and is a theorem, whether the kernel accepts its proof again, the axioms it depends on (`Lean.collectAxioms`, what `#print axioms` prints), and for each `about` constant its kind and whether it occurs in the theorem's statement (its type), and the statement itself as Lean prints it. `exegra verify` records the facts in `evidence/results.json` under `theorems`, each with the hash of the `formal/` sources it was checked on (`formalHash`), the records stamp of the tree (`stamp`) the sha256 of the statement printed with binder names erased (`statementHash`, `hashVersion` 2), the file defining the theorem and the Exegra declarations its statement uses with their files (for `exegra impact`), and, when the claim names a `supersedes` theorem, whether that theorem is a kernel-checked implication from the new statement and the hash of its conclusion; `exegra claims` and `exegra evaluate` check again when Lean is installed (`EXEGRA_NO_LEAN=1` skips it) and otherwise use the recorded facts, as the application does. The rule, applied in Lean (`Exegra.Verdict.theoremOutcome`, called through `claims.status`), turns the facts into a status: `proved` when all hold; `violated` when Lean refuses (no such constant, not a theorem, the kernel rejects the proof, `sorryAx` from `sorry`, `Lean.ofReduceBool` or `Lean.ofReduceNat` from `native_decide`, an axiom of our own, a claim with no `about` constant, an `about` constant that is missing, is `opaque` (a `partial def` and an `implemented_by` opaque compile to one), is reported `implemented_by`, `extern` or `partial`, is not a definition, or does not occur in the statement); `not-evaluated` with no recorded check, and `not-evaluated` with a "Stale:" explanation when the recorded check ran on other `formal/` sources than the current ones (its `formalHash` differs, or it has none): replacing a proof by `sorry` and evaluating without Lean no longer keeps the claim proved. A refusal recorded on other sources still stands. A refused theorem makes `exegra verify` fail unless the claim is expected to be violated. The checker does not yet report `implemented_by`, `extern` or `partial` for a definition, and does not compare the statement with what the claim says: a theorem that mentions the named code but states nothing about it is still `proved` (WG-5690). A change of a claim's theorem is admitted only if it does not weaken it: `exegra admit` refuses, with `admit.theorem-weakened` unless `--accept <claim>` names the claim, a change that removes the theorem, adds an axiom to its proof, changes its `about` set, or changes its statement hash without a `supersedes` theorem of type new statement → old statement that passes the Lean gate (`Exegra.Impact.weakening`).

Requiring the `about` constants in the statement is what makes the theorem about the code: a true theorem that does not mention `Exegra.runInput` says nothing about the engine. What the check does not establish is that the code which runs is those definitions; that is the trusted base, recorded as assumptions of the self-specification (`trusted-lean-kernel`, `trusted-lean-compiler-runtime`, `trusted-emscripten-toolchain`, `trusted-libuv`, `trusted-js-glue`, `trusted-wasm-engine`, `trusted-os-filesystem`, `trusted-js-shell`) and listed by each claim and by the components' `implementation.trusts`.

## Evidence

An `evidence` entity attaches an artifact to a claim: `kind` (`test`, `measurement`, `document`, `review`), `ref`, `supports` (default true; false marks contradicting evidence), `description`, `observed`. Evidence is author-entered and is never a result by itself.

For `external-evidence` claims the status is:

| Attached evidence | Status |
|---|---|
| none | `not-evaluated` |
| any contradicting (declared or recorded `fail`) | `violated` |
| any recorded result that is stale ([Freshness](#freshness-of-recorded-facts)) | `not-evaluated`, explanation "Stale: …" |
| a recorded `pass` of a `test`, or a non-test item | `supported` (the explanation states which part Exegra executed and which is author-entered) |
| only `test` items with no recorded result | `inconclusive` |

`supported` therefore ranges from "Exegra ran this test and it passed" to "someone wrote a document reference". The explanation of each result says which. In the multiplayer test fixture (`tests/fixtures/multiplayer/spec.jsonc`), `ack-latency-objective` is `supported` by a measurement entity marked `illustrative://`, "A placeholder... No such report exists", and the result states that Exegra executed nothing.

## Recorded results

`exegra verify` executes the `test` evidence of a project and writes `specs/<project>/evidence/results.json`, keyed by evidence id:

```jsonc
{ "results": { "ev-roundtrip-core": { "outcome": "pass", "ranAt": "2026-11-14T18:02:54.354Z", "stamp": "4686…" } },
  "traceability": { /* module/file comparison */ },
  "theorems": { /* Lean checks, each with formalHash, stamp and statementHash */ },
  "claimBaseline": { "core-independent-of-ui": { "status": "verified" } /* … each claim of the last passing run */ } }
```

The application and CLI read it when evaluating claims. A `fail` records the last 20 lines of test output. A Node test reference that matches no test (a title pattern that selects nothing) is recorded as a `fail` with the detail "the reference matched no test", not as a pass. A reference passes only when at least one matched test executed and passed and no matched test failed, skipped itself or is a `todo` (a `describe` block is not a test of its own); a reference whose matched tests skipped, wholly or in part, is recorded as `not-run`, and an older pass is not kept for it. Evidence in a realisation root ([verification.md](verification.md#realisation-roots-code-and-tests-in-other-repositories)) is decided from that root's JUnit reports and records `root` and `reports` too; its outcome may also be `not-run` (absent from the report, skipped, errored, or failed for an environmental reason), which counts as no recorded result, never as a pass or a failure. Only evidence of kind `test` is executed.

### Freshness of recorded facts

Every result `exegra verify` records carries `stamp`, the **records stamp** of the tree it was recorded on (`tools/tree-stamp.js`: the tree stamp over every tracked and unignored file and the generated engine builds, without the project's `evidence/results.json` and `generated/`, which Exegra writes from its results), and every Lean check carries `formalHash`, a hash of the `formal/` sources. The command line (`claims`, `evaluate`, `gaps`, `admit`, `generate`, `verify`) evaluates claims against the current stamps:

| The fact | Read as |
|---|---|
| recorded with the current stamp (or formal hash, for a Lean check) | fresh: it counts; the result's `freshness` is `fresh` |
| recorded with another stamp, or with none (results recorded before stamps existed) | stale: a pass establishes nothing, so the claim is `not-evaluated` with an explanation starting "Stale:", `freshness: "stale"` and the diagnostic `claim.stale-evidence` (`claim.stale-theorem` for a Lean check); a `fail` still makes the claim `violated` |
| read where no stamp can be computed (the application in the browser) | unverifiable: shown, but it establishes nothing (only fresh facts give strength), with `freshness: "unverifiable"`, the info diagnostic `claim.freshness-unverifiable` and an explanation that says so (WG-5688) |

An external tool's outcome under `claims` follows the same rule (it needs the current `stamp`). Concordance results are bound by their own `specSha256` (below), not by the stamp. Freshness is a component of the status tuple (`verdict.freshness`), decided in Lean per fact from its recorded and current stamps; the word shown for a claim whose only positive facts are stale is `not-evaluated`. The stamp is coarse: any edit of a stamped file makes every recorded result stale until `verify` runs again.

## Concordance results

A linked project may name a results file written by Concordance, a tool that checks a specification against code, with `"concordanceResults"` in its `project.jsonc` (see [model-and-format.md](model-and-format.md)). Each entry of its `claims` (keyed by claim id, only `pass` and `fail` entries) is applied on load as a derived `test` evidence item, `concordance-<claim id>`, that exists only in claim evaluation. A `pass` makes an external-evidence claim `supported` (never `verified`), a `fail` makes it `violated`, and a claim without an entry stays `not-evaluated`. The explanation names the Concordance result with its `detail` and `proofs`. The file is ignored with a warning when it is missing or invalid JSON, when `tool` is not `concordance`, or when its `source` does not name the project's specification; an entry for an id that is not a claim of the specification is ignored with a warning naming the id. `exegra validate` lists these warnings under `concordance`. Nothing else changes: the derived items are never written to `results.json` and are not spec entities. Tests: `tests/core/concordance.test.js`. A `concordanceResults` path that is a directory (or cannot be read for another reason) is the warning `concordance.unreadable` and changes no status; the project still loads. The file watcher observes the results file too and reports a change as a change of the recorded results, so the application re-reads it and re-evaluates the claims. Tests: `tests/core/concordance.test.js`.

## Conformance stages

Conformance of the implementation to the specification is graded in stages (WG-5685), weakest first. Each is a claim method, `conformance-<stage>`, and the result of such a claim carries `stage`. The Lean verdict's `maxStrength` bounds what each can give: the first five rest on executed test evidence (a fact of kind test), so they give at most `checkedOnInstances` and are never established; `verified-refinement` rests on a Lean theorem checked like a `lean-theorem` claim (`theorem`, `about`), and gives `proved`, subject `implementation`. `tests/core/conformance-stages.test.js` checks each stage. In the self-specification, `camera-restored-per-view` is checked at the trace stage: `tests/core/camera-conformance.test.js` runs the camera code of `src/app/main.js` through leaving a view and coming back, and the machine-level check is `camera-restored-in-model`. An edit of `main.js` makes the recorded result stale without rerunning anything (the records stamp of the tree changes), and rerunning the check on the edited code refutes the claim.

| Stage | Establishes | Does not establish |
|---|---|---|
| `structural` | The code has the parts the specification names: the declared modules exist, every source file is claimed by a component, realisation roots resolve. | That any part does what the specification says; anything about behaviour. |
| `interface` | On the inputs the tests ran, the code accepts and produces the shapes declared: contract requests and responses, payload and record types, telemetry line formats. | That every input of those shapes is handled, or handled as the machines say; ordering or state. |
| `transition` | On the states and events the tests drove, the code reacts as the declared transition: from a specified state, an event leads to the specified next state and outputs. | Transitions or states the tests did not drive; sequences of transitions; interleavings. |
| `trace` | On the scenarios the tests ran, a run of the code produces the specified behaviour: the trace of a claim checked against what the code did. | Other scenarios, inputs or orders; a code change after the recorded run (the result reads stale, [Freshness](#freshness-of-recorded-facts)). |
| `runtime-monitor` | A stream recorded from the running code replays through the specification without a divergence (`src/core/replay.js`). | Runs that were not recorded; behaviour the instrumentation does not report (the recording is the code's own testimony). |
| `verified-refinement` | A kernel-checked theorem states that the implementation refines the specification (for example through `Exegra.Core.LTS.Simulates`, whose `refines_traces`, `refines_safety` and `refines_liveness` carry finite traces, invariants and fair liveness down), about the implementation constants it names. | That the code which runs is those constants: that rests on the trusted base (the Lean compiler and runtime, the WebAssembly toolchain, the JS glue), listed as the claim's assumptions. |

## What Exegra can prove, simulate, and only record

| Boundary | What it covers | Examples from `specs/exegra/spec.jsonc` |
|---|---|---|
| **Established by checking the model** | Structure of the declared components, relationships, ports, properties; evaluated exhaustively over the declared graph. | `core-independent-of-ui`, `core-dependencies-acyclic`, `storage-has-owner`. These are exact over the declared relationships plus the relationships extracted from the code (static imports, provenance `extracted`, `tools/extract.js`); a result says which kinds of relationship it read (`basis`), and claim strength reports the mix. Extraction is trusted (assumption `static-extractor-sound`) and must describe the tree (assumption `extracted-facts-current`, checked by `verify`). |
| **Checked on traces** | Behavior of the specified state machines on listed scenarios and faults. | `rejected-edit-changes-nothing`, `conflict-never-overwrites`, `commit-only-after-validation`. Valid for the listed traces and for the machines as abstractions of the code. |
| **Needs external evidence** | Anything about the real code, tests, hardware, performance or time. | `simulation-deterministic` (supported by `tests/core/sim.test.js` with a recorded pass), `benchmark-scene-interactive` (`not-evaluated`: no measurement exists and no threshold is defined). |
| **Not evaluable here** | Probabilistic or exhaustive properties. | `ack-probability-bound` in the multiplayer test fixture uses `probabilistic-model-check`, which has no evaluator, so it stays `not-evaluated`. |

Seeded and real violations are kept visible on purpose. The multiplayer test fixture carries `ack-implies-durable-under-early-ack` (behavioral) and `database-reached-only-by-runtime` (structural), both violated by design, and the browser tests rely on them. The shipped `exegra` project carries `edits-only-via-transactions`, violated because Import bypasses the transaction pipeline.

## Integrity rules

A claim is about components, behaviors and traces. A consistency rule over the specification itself (no live entity rests on a superseded decision; a decision closes only what names it as resolver) is an **integrity rule** instead: an entity of the built-in kind `integrityRule`, evaluated on every edit, enforced by `Project.apply` as a ratchet, and proved (`holds`, by reflection) or refuted (from a concrete witness) in Lean by `exegra prove-integrity`. The same rule that vacuity is not verification applies: a rule whose quantifier ranges over nothing is reported vacuous, and every rule of the test fixture must be falsified by a stated mutation. See [integrity-rules.md](integrity-rules.md).

## Check strength and grounding

A status says that an evaluator checked a claim within its scope. It does not say how much that check could have found: a `never` claim about an event that only a defect transition emits is verified on every trace, and so is an invariant whose bound is the count its one scenario produces. Every claim and every integrity rule therefore also gets two computed attributes, from a static, deterministic analysis of the model in `src/core/claim-strength.js` (`claimStrength(model, opts)`, a map from id to `{entity, check, grounding, details}`). They never change a status. The definitions, the alternatives considered and why are the decision `dec-claim-check-and-grounding` in `specs/exegra/spec.jsonc` (WG-5274, WG-5276).

**Nominal transitions** are those not `faultOnly`, plus the `faultOnly` transitions a fault of the claim's own scenarios enables. Negatives do not count: they are the defects.

| Check | Meaning |
|---|---|
| `holds-by-construction` | No nominal run can violate the claim. For a `state-invariant`, the expression is true for every combination of the values nominal runs can give what it reads: a variable assigned by no nominal transition keeps its initial value, one set only to literals takes its initial value or one of them, two variables of one behavior that start equal and are always set together to the same expression (one that reads none of the behavior's variables) stay equal, a `state` takes any state reachable from the initial state over nominal transitions, and anything else is unknown. For `never`, and for the `then` of `precedes`, the occurrence can be produced only by fault transitions or by nominal transitions whose guard is false for every such value; an occurrence the scenario script delivers or a fault injects is produced by the scenario, so it never counts. `details.variables` names each variable with what nominal transitions do to it and the fault transitions that assign it; `details.transitions` names the fault transitions. |
| `restated-scenario` | A `state-invariant` that is a plain comparison of one variable with a numeric literal, where nominal transitions change the variable by an expression (a counter), the claim lists one scenario, and the bound is exactly the largest (`<=`, or one more for `<`) or smallest (`>=`, or one less for `>`) value the variable takes in that scenario's run, which changed it. The scenario is run once for this. |
| `single-trace` | Any other trace claim (`state-invariant`, `precedes`, `eventually`, `never`): decided by running hand-written scenarios, with no exhaustive exploration and no refinement. `details.scenarios` lists them. |
| `explored` | A trace claim that an exhaustive exploration (`exegra prove`) found to hold, when the caller passes it in `opts.explored`. Exploration results are not recorded in a project yet, so `claims`, `evaluate`, the report and `admit` do not report it (WG-5280). |
| `refined` | A `refines` claim, or a trace claim whose behaviors all refine an existing behavior. |
| `structural`, `data-model`, `lean-theorem`, `sampled`, `test`, `evidence`, `integrity`, `none` | The method: the structural methods, `data-model`, `lean-theorem`, `metric-bound`, external evidence with a test attached, other external evidence and external verification methods, an integrity rule, and no method or one this build does not evaluate. |

Vacuity is decided first: a claim that holds by construction stays `holds-by-construction` even when it was explored.

| Grounding | Meaning |
|---|---|
| `bound` | The check reads the platform's own entities: the component graph (structural methods), records and copies (`data-model`), Lean definitions (`lean-theorem`), the entities of the kinds an integrity rule quantifies over, or behaviors that are anchored and branch on no free input. |
| `partly-bound` | Some of what it reads is bound and some is not: an anchored behavior that also reads a free input, a claim reading one anchored and one unanchored behavior, or a `data-model` claim restricted to records the change adds. |
| `self-contained` | The behaviors it reads are not anchored: their guards and effects read only their own variables, `time` and free inputs, which the scenarios supply as literals. |
| `not-applicable` | The status rests on evidence outside the model, or nothing is evaluated. |

A behavior is **anchored** when it refines an existing behavior, is stored in a record (`storage.record` or `instances.storedIn`), reacts to or emits an event of a contract (the details name the capabilities in the contract's `auth.requires`), or reads the state or a variable of an anchored behavior. A **free input** is a payload field of an event that belongs to no contract, read by a guard or an effect of a nominal transition; `details.free` lists them. The behaviors a trace claim reads are those its expression names, the owner of a transition matcher, and for an event matcher the behaviors of its scenarios that react to or emit the event. A behavior's `subject` component does not anchor it: every behavior has one. The expression language cannot read roles, capabilities or grants, so the access model reaches a behavior only through a contract, and integrity rules are where it is quantified over. With `opts.existing` (the ids the platform already has; `admit` passes the specification before the change) an entity outside it anchors nothing.

Examples from the Harbourline fold (WG-5265): `hl-chk-rx-continuous-renewal` (`clockRestarts == 0`, incremented only by the fault `hl-rx-renew-restarts-clock`), `hl-chk-wv-clock-from-receipt` (`clockStart` and `receivedAt` set together from `time`) and `hl-chk-au-append-only` (`hl-au-edited` emitted only by a fault) are holds-by-construction; `hl-chk-gf-no-creation-after-loss` (`featureRecords <= 1`) is restated-scenario; `hl-chk-ag-forbidden-refused` is single-trace and self-contained, its behavior deciding on `event.changesPower`; the integrity rule `hl-agent-roles-hold-no-forbidden-power`, over every role, is bound.

What it does not find: the value analysis ignores guards when it collects values and reachable states, does not follow arithmetic, and does not analyse behaviors with `instances` or aggregate references, so vacuity that depends on them is not reported; `restated-scenario` examines only a plain comparison. Grounding is structural: an anchored behavior can still decide on a field that means nothing, and a contract event's payload is still supplied by the scenario.

`exegra claims` and `evaluate` add `check`, `grounding` and `strength` (the details) to each result; the claims report shows them per claim and counts them; `exegra admit` counts them before and after a change and gives each claim the change creates that is vacuous, single-trace or self-contained an acknowledgeable reason ([agent-interface.md](agent-interface.md)). Tests: `tests/core/claim-strength.test.js`.

## Where results are shown

The *Verification* tab lists claims by status with scope, explanation, assumptions, evidence (declared versus recorded) and counterexample, and selecting a claim highlights its involved entities in the 3D scene; the `claims` projection draws a claim's entities colour-coded by status. Author-entered evidence is never drawn in a verified or supported colour: an evidence edge that supports is steel and one that contradicts is red. `node cli/exegra.js claims --project <name>` and `evaluate [<claimId>]` print the same results; `generate` writes `claims-report.md` and `.json`, with the check and grounding of each claim. The *Verification* panel shows recorded results loaded with the project and cannot execute tests.
