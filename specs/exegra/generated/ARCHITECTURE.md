# Exegra

A bidirectional, executable, visual specification environment for software systems, and its own first subject. The JSONC specification text is the single authority; the 3D scene, inspector, source editor and agent command line are views of, and editors for, one transactional semantic model.

Generated by Exegra from the semantic model. Semantic hash 1a2d18c9095287. Do not edit; regenerate.

### Meta-model

Describes entity kinds, their properties, the built-in categories and relationship kinds and the top-level sections of a specification as data.

- Category: Data store
- Parent: Semantic core (`semantic-core`)
- Owner: semantic-core

#### Responsibilities

- Define which properties each entity kind accepts and their types
- Define the built-in vocabulary (categories, relationship kinds, shapes, colours, projections) that a specification may extend
- Define the id pattern and the schema version (0.1)
- Define the claim kinds (structural, invariant, temporal, measured, requirement) and the view definition: filter (categories, relationship kinds, within, tags, entity kinds) and display (ports, colour by, reference depth, layout method)
- Define the record and copy kinds of the data model: field types, personal-data classes, roles, copy scopes (shared, per-session, per-principal, internal) and the units of freshness and erasure bounds

#### Relationships in

- Reads → Parser: Checks structure and property types against the entity definitions in metamodel.json.
- Reads → Transaction system: Reads the id pattern.
- Reads → Edit dialogs: Reads the id pattern and checks ids with it.
- Reads → Data model: The record and copy kinds and their enums are declared in the meta-model.

#### Known unknowns

- The built-in entity kinds, claim kinds, claim evaluation methods and projections are fixed per build. A specification can add entity kinds, properties of any kind, categories, relationship kinds and verification methods (carried out outside Exegra) through its vocabulary, but it cannot add an evaluation method that Exegra itself runs.

#### Implementation

- Status: manual
- Modules: `src/core/metamodel.json`
- Notes: Hand-written data file.

### Parser

Derives the semantic model from JSONC source text and records where every entity is declared.

- Category: Logical module
- Parent: Semantic core (`semantic-core`)

#### Responsibilities

- Parse JSONC with comments and trailing commas, reporting syntax errors with locations
- Check structure, types and references against the effective meta-model (built-in meta-model plus the specification's own vocabulary)
- Build the effective meta-model from the vocabulary section: categories, relationship kinds, entity kinds (each with its own top-level section, shape, colour and properties), reference-typed and list-typed properties on any kind, and verification methods; report a malformed, unknown or duplicate definition as a diagnostic
- Look up spec-supplied keys only as own properties, so a key such as constructor never resolves to something inherited
- Index every reference and expression with its source path
- Report unsupported constructs as diagnostics instead of dropping them
- Index the scenario and fault references inside a trace claim's negatives, so rename and delete follow them

#### Relationships out

- Reads → Meta-model: Checks structure and property types against the entity definitions in metamodel.json.
- Reads → Claim method registry: Imports CLAIM_METHODS to check evaluation parameters.
- Calls → Model queries: Imports the own-property lookup that keeps spec-supplied keys from resolving inherited properties.
- Depends on → jsonc-parser: Builds the syntax tree and reports syntax errors with the library.

#### Relationships in

- Calls → Validator: analyzeSpec calls parseSpec, then validates the model.
- Calls → Transaction system: Re-derives the model after every text edit and parses a replacement source.
- Calls → Source editor: Parses the draft to find the location of an entity to reveal.
- Calls → Test suites: Core tests exercise parsing and normalization.

#### Known unknowns

- The whole text is re-parsed on every commit and on every source-editor analysis; there is no incremental parsing and no measurement of its cost on large specifications.
- The schema.version error message tells the user to run an `exegra migrate` command that does not exist.

#### Implementation

- Status: model-configured
- Modules: `src/core/parse.js`
- Notes: Structure checks are driven by metamodel.json and the specification's vocabulary; the parser code itself is hand-written.

### Validator

Applies whole-model semantic rules to a parsed model and reports errors, warnings and specification gaps; analyzeSpec composes parser and validator.

- Category: Logical module
- Parent: Semantic core (`semantic-core`)

#### Responsibilities

- Check containment, behaviors, transitions, effects, faults, scenarios, claim parameters and views
- Accept an evaluation method the specification declares as a verification method (it takes no parameters), and report any other method this build does not run as unsupported
- Check every expression's references against the scope it is used in
- Report gaps (missing purpose, unconnected component, unused event, claim that can only rest on external evidence and has none) as info diagnostics; a requirement claim is not reported for lacking evidence
- Provide analyzeSpec: parse, then validate only when the structure is sound
- Check events that name a contract: a role is required, the payload fields are among the inputs (request) or outputs (response), every input that is not optional is present, an error carries a code among the contract's errors, and declared field types are assignable to the contract's; an unknown contract is a reference error
- Run the data model's consistency checks (record keys and copy fields name declared fields, bounds have units) as errors and its five data rules as warnings, each naming the record or copy and the field
- Check each negative of a trace claim: its scenario is one of the claim's scenarios, and its faults are a non-empty list of declared faults none of which that scenario already activates
- Report integrity rules: an invalid rule as an error, a vacuous rule as a warning, and each violation with the rule severity (integrity.violated), left out of analyzeSpec's blocking error count

#### Relationships out

- Calls → Model queries: Imports the own-property lookup for the verification methods, claim methods and relationship kinds a specification names.
- Calls → Parser: analyzeSpec calls parseSpec, then validates the model.
- Calls → Expression language: Parses guards, effect values and claim expressions and lists their references.
- Reads → Claim method registry: Checks each claim's method and parameters against the registry.
- Calls → Fault model and environment: Runs the fault model rules (missing sources, bounds, realises outside the model) as part of validation.
- Calls → Contract conformance: Checks the payload of every contract event against the fields, types and errors of its contract.
- Calls → Data model: Runs the data rules and the record and copy consistency checks as part of validation.
- Calls → Integrity rules: Reports invalid rules, vacuous rules and every current violation as diagnostics.

#### Relationships in

- Calls → Transaction system: Project calls analyzeSpec on every candidate specification and refuses results with errors.
- Calls → Toolbar: Import analyzes the bundle's spec.jsonc with analyzeSpec and refuses it when it has syntax errors.
- Calls → Source editor: Analyzes the draft with analyzeSpec for its diagnostics.
- Calls → Specification checker: Analyzes the file with analyzeSpec.
- Calls → Benchmark generator: Checks that the generated specification analyzes.
- Calls → Test suites: Core tests exercise the validation rules.

#### Implementation

- Status: manual
- Modules: `src/core/validate.js`, `src/core/analyze.js`
- Notes: The rules are hard-coded. Claim parameter checks read the claim method registry, the gap rules read `expected` flags of the effective meta-model and view filters are checked against the effective vocabulary.

### Transaction system

Applies typed operations atomically as source-preserving text edits, with revisions, undo, redo, reload and commit notification; it is the only place where a project's state changes.

- Category: Logical module
- Parent: Semantic core (`semantic-core`)

#### Responsibilities

- Check operation preconditions and compute JSONC edits that keep comments and formatting
- Reject any transaction whose resulting specification has validation errors (violations of integrity rules excepted) or whose layout would be unreadable; nothing changes on rejection
- Keep presentation edits (layout) out of the specification text
- Record history sufficient for undo and redo and increment a revision on every commit
- Adopt text that changed outside the process (reload): text with syntax errors is refused, any text that parses is adopted, including text with validation errors; the adoption clears the undo and redo stacks and is itself not undoable
- Leave the model and its semantic hash as they were when a commit changes only presentation text
- Notify subscribers synchronously after each commit
- Reject a transaction that adds a violation of an integrity rule of severity error that the project did not have before (the ratchet), with the counterexamples; existing violations do not block unrelated edits

#### Ports

| Name | Id | Direction | Contract | Protocol |
| --- | --- | --- | --- | --- |
| Apply transaction | transactions-apply-in | provides | Apply a transaction | in-process call (Project.apply) |

#### Relationships out

- Calls → Parser: Re-derives the model after every text edit and parses a replacement source.
- Calls → Validator: Project calls analyzeSpec on every candidate specification and refuses results with errors.
- Calls → Expression language: Operations parse expressions when renaming ids that expressions mention.
- Calls → Model queries: Finds declaration sites and owned entities when creating and deleting.
- Reads → Meta-model: Reads the id pattern.
- Calls → Normal form and hash: Computes the semantic hash of each committed model and the text hash of a project.
- Depends on → jsonc-parser: Computes and applies the minimal text edits that keep comments and formatting.
- Data flow → Application session: Each commit delivers its TransactionResult and history entry to the listener the session subscribed.
- Calls → Integrity rules: Project.apply refuses a transaction that adds a violation of an error rule (the ratchet).

- Reads → Application session: Reads the committed model, diagnostics, texts and revision from the project; the UI reads them through the session.
- Subscribes → Application session: Registers its commit listener with Project.subscribe; the project knows it only as a callback.
- Submits edits to → Application shell: Ctrl+Z, Ctrl+Shift+Z and Ctrl+Y call undo and redo on the project through the session.

### Claim evaluator

Evaluates claims against a model and recorded evidence results, reporting a status, scope and counterexample that never overstate what was checked.

- Category: Logical module
- Parent: Semantic core (`semantic-core`)

#### Responsibilities

- Evaluate structural claims (no-relationship, reachable, only-via, has-port, property-defined, acyclic) on the component graph; report a selector that selects nothing as inconclusive, never verified; reachable needs a path of at least one relationship (a target that is also a source does not count)
- Evaluate invariant and temporal claims on traces of the listed scenarios (state-invariant, precedes, eventually, never), stating that only those traces were checked; never report a vacuous trace check as verified: an implication whose antecedent is never true, a never whose event cannot occur, a precedes whose then-event never happens and traces with zero steps are inconclusive
- Derive the status of external-evidence claims only from evidence entities and recorded execution results
- Report a claim whose method is a verification method declared by the specification with evaluator external:<method>: Exegra runs nothing and the status comes only from evidence
- Check a trace step by step for the simulator panel (checkTrace)
- Add the automatic contract-conformance checks of a trace to the checks of checkTrace (src/core/contract-trace.js), as failed checks with the step
- Evaluate data-model claims (method data-model, a list of rules) on the records and copies of the model: violated with the first finding as counterexample, verified when every listed rule had something to check and found nothing, inconclusive when a listed rule had nothing to check
- Run every declared negative of a trace claim (its scenario with the scenario's own faults plus the negative's) and report the claim verified only when it holds on its scenarios and each negative, at least one, violates it; a trace claim with no negative, or with a negative that does not definitely violate it, is inconclusive and the explanation says which

#### Ports

| Name | Id | Direction | Contract | Protocol |
| --- | --- | --- | --- | --- |
| Evaluate claims | claims-evaluate-in | provides | Evaluate claims | in-process call |

#### Relationships out

- Reads → Claim method registry: Dispatches only on registered methods; an unregistered method stays not evaluated.
- Calls → Model queries: Builds the component graph and selects components for structural claims.
- Calls → Expression language: Evaluates claim expressions against trace configurations.
- Calls → Normal form and hash: Stamps every result with the semantic hash it was computed from.
- Calls → Simulation engine: Runs the listed scenarios for invariant and temporal claims.
- Calls → Refinement checker: Refinement checks are claims.
- Calls → Exhaustive explorer: Claims evaluated exhaustively within bounds (planned, WG-4650).
- Depends on → Fault model and environment: States the fault model in each claim result's scope.
- Calls → Implementation refinement checker: Refinement of implementation traces is a claim (planned, WG-4679).
- Calls → Proof export: Claims proved in Lean are reported as verified by proof (planned, WG-4686).
- Calls → Contract conformance: checkTrace adds the automatic checks of the contract events of a trace.
- Calls → Data model: Evaluates data-model claims from the findings of the data rules.
- Calls → Metric claims: Metric-bound claims are evaluated by the metric claims component (planned, WG-4715).

- Calls → Agent command line: Evaluates claims for claims, evaluate, trace and verify.

### Simulation engine

Executes the state machines of a scenario as a deterministic discrete-event simulation over logical time.

- Category: Logical module
- Parent: Semantic core (`semantic-core`)

#### Responsibilities

- Order events by logical time and scheduling sequence, deliver each to every behavior of the scenario
- Fire at most one transition per behavior and event, evaluating guards against the configuration at the start of the step
- Apply faults (drop, delay, enable or disable a transition, inject an event) and record them in the trace
- End a run as quiescent, step-limit (default 1000) or error
- Run as one engine everywhere: the Rust crate engine/exegra-engine, compiled to WebAssembly and loaded only through src/core/engine.js in the browser and in Node (the Simulation tab runs it in a Web Worker so a long run never blocks the page), and as the native binary exegra-sim

#### Ports

| Name | Id | Direction | Contract | Protocol |
| --- | --- | --- | --- | --- |
| Run scenario | simulation-run-in | provides | Run a scenario | in-process call |

#### Relationships out

- Calls → Simulation aspect registry: Runs the hooks of the aspects a specification enables (planned, WG-4665).
- Depends on → Formal semantics (Lean 4): The engine is checked against the formal semantics, which defines what it must compute (planned, WG-4685).
- Calls → Resource model: Settles resources after each step and runs service-done and wait-timeout entries (planned, WG-4664, WG-4715).

### Projection system

Derives a flat scene (nodes, edges, legend, notes) from the model for a declared view with one of five projections (structural, claims, behavior, references, data); a view is never a separate dataset and every node and edge is backed by a real entity.

- Category: Logical module
- Parent: Visualization (`visualization`)

#### Responsibilities

- List the views declared in the specification, plus an implicit view for each projection type without a declared view
- Project the structural, claims and behavior projections, applying view filters (categories, relationship kinds, within, tags) and display options
- Project references: the focused entity (the session's selection) and every entity within display.depth reference hops (1 to 3, in either direction, any entity kind, declared kinds included), at most 150 nodes with a note naming what was left out; filter.entityKinds restricts the kinds drawn, and without a focus it draws every entity of those kinds when there are at most 300, otherwise only a note asking for a selection
- Handle collapsed subsystems (lifted edges), hidden entities, isolation, claim focus, scenario focus and the current simulation step
- Take node shapes, colours and line styles from the effective vocabulary of the model; entities of declared kinds take the shape and colour their kind declares
- Derive the message flow of a simulation step (src/core/flows.js): the sender is the subject of the behavior whose transition emitted the event, or outside for a scenario stimulus or an injected fault; the receivers are the subjects of the behaviors that fired on it; the path follows the scene edge between their drawn nodes, and is marked unshown when only a relationship the view does not draw connects them, or undeclared when none does

### Layout engine

Computes deterministic layouts of a scene on the ground plane by one of four methods, recursively over containers, honouring pinned leaf positions, and can choose the method by scoring the results.

- Category: Logical module
- Parent: Visualization (`visualization`)

#### Responsibilities

- Offer the methods layered (dependency layers left to right), layered-down (front to back), packed (no flow direction, connected siblings in tight rows) and radial (best-connected node at the centre, rings around it); each arranges the siblings of one container level and the shared recursion encloses them in their container with padding
- Place pinned leaf nodes at their absolute [x, z] pin and keep their container enclosing them
- Tolerate cycles, self edges and edges across containers
- Shape the result towards a target width-to-depth ratio supplied by the caller (default 1.6)
- chooseLayout (method auto): compute every method, score each placement (aspect against the target, mean edge length, edge crossings, whitespace area, fixed weights) and return the lowest score, ties going to the earlier method, together with every score

#### Relationships out

- Projects onto → Three.js scene renderer: Derives the placement of the scene's nodes on the ground plane.

#### Relationships in

- Data flow → Application session: The projected scene, the pins of the active view, the requested method (auto or one of the four) and the viewport's width-to-height ratio travel to the layout engine; the placement, the method used and, for auto, the scores come back as the return value.
- Calls → Application session: Lays the scene out with the pins of the active view from the layout file: chooseLayout with the viewport's aspect when the view's layout is auto, layoutScene with the chosen method otherwise.
- Calls → Test suites: Core tests exercise the layout.

#### Known unknowns

- Pins are absolute positions; nothing re-anchors them when the model changes.
- The score weights are fixed constants chosen by hand; no recorded measurement shows that the lowest score is the most readable layout. Crossings are counted on at most 400 sampled edges.
- Automatic layout computes all four methods on every recompute; its cost on large scenes has no recorded measurement.

#### Implementation

- Status: manual
- Modules: `src/core/layout.js`, `src/core/layout/constants.js`, `src/core/layout/model.js`, `src/core/layout/solve.js`, `src/core/layout/layered.js`, `src/core/layout/packed.js`, `src/core/layout/radial.js`, `src/core/layout/score.js`
- Notes: layout.js is the entry (layoutScene, chooseLayout, LAYOUT_METHODS, scorePlacement); the other modules hold the shared recursion (solve.js, model.js), the four arrangers, the score and the shared sizes.

### Three.js scene renderer

Draws a SceneModel and its placement in 3D with Three.js, as a function of (scene, placement, selection, highlight, camera) with no domain state of its own.

- Category: Computational service
- Parent: Visualization (`visualization`)

#### Responsibilities

- Diff the scene incrementally by node and edge id and animate placement changes
- Draw node shapes, container slabs, edge curves with line styles, status colours and CSS2D labels with clutter management; the label layer is its own stacking context, so a label (even a message in flight, lifted above the other labels) never covers the interface around the scene
- Run a requestAnimationFrame loop that renders only when something changed, and report frame statistics
- Detect picking, hover, double click, dragging of leaf nodes and connect-mode clicks and report them through callbacks; it never edits the model. Touch: a tap allows 10 px of movement, a second finger makes the gesture a pinch or pan with no tap, and a node is dragged only after the finger has rested on it for 350 ms (a swipe that starts on a node orbits the camera)
- Animate a simulation step's message: a marker labelled with the event travels from the sender's node along the drawn edge to each receiver (backwards along it for a reply), drops in from above for a request from outside, travels straight for a relationship the view does not draw, and travels straight in the violation colour when no relationship is declared; only the current step's message is in flight, so stepping quickly or playing never piles markers up

### Markdown importer

A command line tool that converts a Markdown specification, structured Markdown kept in another repository, into the specification file of a linked project, a specification that declares its own entity kinds and verification methods.

- Depends on → jsonc-parser: Reads the project's import map with the library.
- Calls → File system: Reads the Markdown tree and the import map, and writes or compares the generated file, with node:fs.

- Calls → Register importer: Reuses the Markdown importer's text helpers, loss collection, coverage comparison and git commit reader.

#### Known unknowns

### Exhaustive explorer

Explores every configuration of a scenario reachable within a bound, over every order of delivery of simultaneous events and every subset of the scenario's faults, with state deduplication. It reports that a state invariant holds in all N of them or returns a counterexample run, and it checks the temporal claims never, precedes and eventually on every complete run (a run ends at quiescence, at the step limit or in a failed step) by searching the product of the explorer's state with a small monitor. The explorer is defined in the Lean semantics and proved sound there; a faster explorer in the Rust engine (WG-4650) is to be checked differentially against it.

- Category: Logical module
- Parent: Semantic core (`semantic-core`)

#### Responsibilities

- Define the nondeterminism a scenario admits as a successor relation over configurations: which of the pending entries with the head's time is delivered next, and which subset of the scenario's faults acts in the run; the deterministic step is one of the successors (step_mem_successors)
- Explore breadth-first with a visited set under a bound on steps and a budget of states, and return holds with the number N of distinct states visited, a counterexample (a fault choice and delivery choices), or incomplete when the budget runs out
- Prove that holds means the invariant holds in every state reachable within the bound (explore_sound) and that a counterexample is a run of the successor relation within the bound that ends with the invariant false (explore_counterexample_real), with only Lean's standard axioms
- Report "verified by Lean for all N configurations within the bound" distinctly from trace-level checks
- Define the temporal forms never, precedes and eventually over finite runs of the successor relation exactly as checkTrace reads them on a trace (a matcher is a delivery of an event or a firing of a transition; precedes allows the first event in the same step as a transition; eventually reads its expression in the final configuration of the run), and check them with a generic breadth-first search (Search.lean) over the explorer state with a monitor (Temporal.lean)
- Prove the monitor agrees with the trace-level definition of each form (never_monitor, precedes_monitor, seen_monitor), that the search replays real runs (greplay_nodes), that holds means the form holds on every complete run (tcheck_sound) and that a counterexample is a real run that violates it (tcheck_counterexample_real); paths cut off by the bound or the state budget, and runs that end without quiescence and would violate or cannot decide an eventually, are reported incomplete, never holds

#### Relationships out

- Calls → Simulation engine: A Rust explorer with the same semantics as simulation, for state spaces too large for the Lean one, checked differentially against it (planned, WG-4650).
- Depends on → Fault model and environment: Explores every subset of the scenario's faults; the concurrency bounds of its fault model are to be applied once the engine input carries them.
- Depends on → Formal semantics (Lean 4): The successor relation takes the semantics' deterministic step after each choice; the explorer runs the semantics' own step function.

#### Relationships in

- Calls → Claim evaluator: Claims evaluated exhaustively within bounds (planned, WG-4650).
- Depends on → Deployment model: Cutover, rollback and migration claims are checked exhaustively.
- Depends on → Proof export: Counterexamples to induction come from bounded exploration.

#### Known unknowns

- The engine input (format version 1) carries no bound of a scenario's fault model, so every subset of the scenario's faults is explored; the concurrency bounds of fault models are not applied yet.
- A fault acts for the whole run or not at all: a fault without an occurrence cannot act on some deliveries of its event and not on others.
- Breadth-first order makes a counterexample one of the fewest steps, but that is not proved.
- The Rust explorer for large state spaces is not built yet (planned: WG-4650); it will be checked differentially against this one.
- Evaluation errors and failed steps end a path without being reported as such: a configuration whose invariant cannot be evaluated counts as a violation, and a failed step has no successor.
- Format 2 inputs are not explored yet (planned: WG-4664, WG-4715). The specified relation adds internal entries to the simultaneous-order choice, the new fault kinds to the mask, and one successor per choice value and per instance of an any route; sampled draws are fixed by a seed named first in the result, and a result is shown as verified only when the scenario has no sampled site. Scenarios with workloads need a short horizon and maxArrivals, and keyed populations of thousands of clients are beyond reach. When a timed fault acts is not explored (WG-4704).
- Temporal claims are checked without the claim's negatives and without the trace check's vacuity rules (a never whose matcher cannot occur in the scenario holds here without a note).
- A violating prefix of a never or precedes claim is reported as the counterexample, not extended to a complete run; any extension violates it too, but that is not a theorem.

- Notes: formal/Exegra/Explore.lean: State (fault mask and Config, with decidable equality and hashing), successors, Reachable, the explorer explore with a Std.HashSet visited set, and the theorems step_mem_successors, explore_sound and explore_counterexample_real, whose axioms are pinned with #guard_msgs. ### Proof export

Exports a scenario's engine input and its state-invariant and temporal (never, precedes, eventually) claims to a Lean file whose theorems state the verified explorer's result per claim, checks the file with Lean and reports each claim as verified (for all N configurations within the bound, or on every complete run), a counterexample run, or incomplete, with the axioms the proof uses. Proving invariants for every reachable configuration at every depth, by induction, is planned (WG-4686).

- Category: Logical module
- Parent: Semantic core (`semantic-core`)

#### Responsibilities

- Build the scenario's engine input exactly as simulate does and collect the state-invariant and temporal claims that list the scenario and apply to it; a claim that names behaviors or an expression outside the scenario is reported not evaluable
- Write formal/generated/<scenario>.lean: the engine input text, its decoded Lean term checked against it (input_decodes), and per claim a theorem explore env (claimInv expr) bound maxStates = result, discharged by native_decide
- Check the file with Lake, loading the modules' compiled code, and report per claim the method lean-exhaustive, the bound, N, the theorem, the file, the axioms and what is trusted
- Render a counterexample as simulate shows a run: the step list with the delivery choices, the active faults, and the request-log lines of contract events
- For a temporal claim write the theorem tverdict form env bound maxStates = result (from the exegra-lean temporal protocol), whose meaning is tverdict_sound and tverdict_real, and render a violating run with the reason in the trace check's words

### Resource model

Resources with capacity, request classes, queue disciplines and bounds, and the service demand of transitions: the part of format 2 that makes a pool, a connection limit or a CPU a queueing station.

- Category: Logical module
- Parent: Semantic core (`semantic-core`)

#### Responsibilities

- Hold per resource its capacity, discipline (fifo or priority), request classes with priority, reserved units (at most the class limit), limit, queue bound and maximum wait, the overflow rule (refuse, drop, shed-oldest) and an optional load-dependent demand factor: a step table (the last row holds beyond it) or exact USL parameters evaluated at each grant
- Record the use, acquire and release effects in phase 2 and apply them when the step settles: release, enqueue, grant by discipline and eligibility, then class bounds in declaration order and the resource bound; holdings are tracked per instance, resource and class, and release names its class
- Draw service demand at the grant from the stream demand:<behavior>:<transition>:<effect> (effect index from 0), against the faults active at that time, and scale it once, rounding up, by the demand factor of the occupancy at the grant and by the combined scale-demand factor reduced to lowest terms (a part of 2^32 or more, or a service time of 2^53 or more, is a failed step); the service time is fixed at the grant
- Delete a request's wait-timeout entry on every path that removes it (grant, bound refusal or drop, shed, crash), so a wait-timeout step always finds its request
- Refuse statically a request whose units can never be granted, also after the fault mask is applied
- Apply scale-demand, set-capacity, set-class-limit, collapse-classes and replace-demand, untimed or within windows through fault-edge steps, the value in effect being a function of the active set (last in the input's faults order, product for scale-demand, any for collapse), without preempting held units; return waiting requests to their own classes when a collapse ends
- Apply crash-instance: an incarnation per instance, recorded on targeted, routed and from fields and on the instance's service-done and wait-timeout entries; at the crash remove timers, waiting requests with their timeouts and in-service requests with their service-done entries, release holdings, draw the restart time, broadcast notify; drop stale entries per behavior; restart edges restore only their own incarnation; a crash of a missing or down instance does nothing
- Keep held units within class limits and capacity, and waiting requests within their bounds, as invariants proved of the step; deadlock freedom is not guaranteed and is left to claims and the explorer

### Workload model

Workloads that drive a scenario from outside its behaviors: open arrival processes (constant, Poisson, ramp, step, on/off, attack floods) with client and address identities and payload generators, closed populations with think time, populations of client behaviors, links with bandwidth, latency, ordering and fan-out, and timers.

- Category: Logical module
- Parent: Semantic core (`semantic-core`)

#### Responsibilities

- Generate open arrivals as instants of b entries, one future instant per workload in the queue, computed from the scheduled time of the previous instant when its original first entry is taken (a delayed copy is never first, and a per-workload count of created instants creates each instant once); draw, in this order, the instant time (Poisson, spent draws included), the batch size, then per entry the client and the payload fields; stop at the horizon
- Validate phases (from < until, sorted, non-overlapping, repeat at least the last until; rates count instants) and schedule constant phases exactly, with j reset per phase and repetition, and Poisson phases (constant or ramp) by inverting the integrated rate against a unit exponential sample, with exact integer square roots and rounding to the nearest base unit: one draw per instant, no thinning and no rejection loop; refuse a phase whose mean interarrival is below 100 base units
- Attach the request id, the client and the address; group users onto addresses by a drawn group-size distribution (sizes below 1 count as 1)
- Run closed populations (issue with a workload-wide request counter, wait for the matching reply, think; a timeout ends the request with outcome timeout and a late reply is ignored) and population workloads whose clients are keyed instances of a behavior created at the start of the run
- Send emits over links: FIFO transfer with time ceil(size * perSecond / bandwidth), then at link-done the latency draw, the delivery entry and the next transfer; ordered links deliver in send order; fan-out keeps one bounded queue per receiver at the link's full bandwidth and drops its oldest waiting message, never the one in transfer
- Set, replace and cancel named timers by their stable id, so that a delayed timer is still cancelled
- Lower specification-level rates, durations and distributions to integers and tables on unbounded BigInt: the exponential and normal quantile tables defined by integer algorithms (exp and ln in 96-bit fixed point, a 192-bit fixed-point normal CDF with bisection), equal to the correctly rounded values and pinned by the SHA-256 a23cd2a9566c106701375d5cf75ef982b8db6f3e52c199c47e6239649c840950 of their canonical text; log-normal sigma at most 8; a lowered value of 2^53 base units or more is a lowering error

#### Relationships out

- Depends on → Formal semantics (Lean 4): Arrivals, links, latency, timers and the SplitMix64 streams are defined in Lean first (planned, WG-4715).

#### Relationships in

- Calls → Simulation engine: Queues the next arrival of a workload when one is taken, runs link transfers and timers (planned, WG-4715).
- Calls → Simulation contract: Lowers workloads, rates, durations, distributions and links into the version-2 engine input (planned).
- Depends on → Load aspect: The load aspect drives scenarios with the workloads of format 2 (planned, WG-4668 on WG-4715).

### Performance metrics

The measured outputs of a run as a pure function of its steps: throughput, outcomes, utilisation, queue length, waiting time, response-time percentiles, false positives, transition counts, link use and cost, per resource, class, link and boundary, over a declared window and in time series, all as integers; and meters, windowed measurements that behaviors read.

- Category: Logical module
- Parent: Semantic core (`semantic-core`)

#### Responsibilities

- Follow the request lifecycle of docs/simulation.md: a request starts when its start entry is first taken as head, ends as error at once when that entry is dropped, crashed, stale or handled by no transition, ends at the first delivered end event with its key (delivered: head of a deliver step that does not fail), ends as timeout on a closed-client timeout, and is otherwise censored; count unkeyed starts, duplicate starts and late ends
- Give ok requests the sample end - start and every other outcome and censored request +infinity; count samples as measured requests started, so a lost or refused request still counts; waiting time is one sample per request enqueued, +infinity when removed without a grant
- Treat underpowered statistics by who starts the class: for open-started classes an underpowered run is left out and a null bucket skipped; otherwise both do not satisfy; time-to-recover always needs every bucket of its hold range non-null and satisfying
- Integrate piecewise-constant signals over [warmup, horizon), with the value in effect at warmup and the last value held to the horizon, and the utilisation denominator the integral of the capacity in effect
- Report nearest-rank percentiles, bucketed series on a grid that divides the window exactly, time-to-first and time-to-recover as durations t - after, and series aggregates max, min and mean; claims scoped to a phase or sub-window
- Compute meters over (t - window, t] from the start-of-step configuration, with null for an empty window or a zero denominator and +infinity samples counted in quantile meters
- Compute cost as counted quantities times exact rational prices, per price, in total and per bucket, for the cost aspect (WG-4669) to report

### Metric claims

Claims over measured outputs, evaluated over many seeded runs with exact binomial and sign tests, reported with their sample count, seeds and confidence as model results (model-holds), never as verified or supported, and validated against recorded load runs.

- Category: Logical module
- Parent: Semantic core (`semantic-core`)

#### Responsibilities

- Declare the claim method metric-bound: scenarios, metric (kind, subject, statistic, outcomes, window, series aggregate), op and bound, approx, or relativeTo another metric with its own window, fraction, confidence, runs, base seed, negatives (on the claim's scenarios or on variants declaring variantOf), control negatives and calibratedBy
- Run the scenario once per seed, run r using the r-th SplitMix64 output of the base seed (mod 2^64), in metrics mode, and take one statistic per run; a truncated run does not satisfy the bound; an underpowered run is left out when only open workloads start the class and counts as not satisfying otherwise; the test uses the thresholds of the N' runs kept
- Decide model-holds, fails or inconclusive by exact rational binomial tails with N fixed in advance (the minimum N is the smallest with beta^N <= alpha, compared exactly); for approx, use the sign-test order-statistic interval of the median of the per-run statistic, which needs at least 6 runs at 95%
- Report model-holds (never supported or verified) with the scope "model only; parameters as stated", runs, seeds, passes, N', fraction, confidence, the spread of the per-run statistic and the underpowered and truncated runs
- Require each negative to fail and each control negative to hold before reporting model-holds; a base scenario that fails makes the claim violated; fixture results test the engine and method and are not evidence about any system
- Check calibrations on hold-out load runs distinct from the fitting runs, with equal workload, capacities and window, a band widened over repeats, at least 6 kept runs and no truncated run, tolerance no wider than the margin computed from the beta-quantile of the per-run statistic, evidence not expired at the recorded asOf date and bound to the current component revisions; report unvalidated otherwise, and extrapolated outside the convex hull (exact rational linear programming) of the tested points with the same fault set
- Vary every assumed and to-be-measured parameter over its declared range, one at a time and then pairwise among the flagged ones, and list first what flips the verdict
- Refuse at validation a run count that could never hold, and a quantile or mean claim whose expected samples from declared open-workload rates are fewer than 30, per bucket for series claims

#### Relationships out

- Calls → Simulation engine: Runs the claim's scenarios once per seed in metrics mode (planned, WG-4715).
- Reads → Performance metrics: Takes one statistic per run from the measured outputs (planned).

#### Relationships in

- Calls → Claim evaluator: Metric-bound claims are evaluated by the metric claims component (planned, WG-4715).

- Run a scenario (`run-scenario`): consumer, via `metric-claims-calls-simulation-engine`

### Register importer

A command line tool that converts one large Markdown specification file, written as headings, prose and register tables, into the specification file of a linked project: every table row becomes an entity of a kind the import map declares (or a generic table row), and every entity names the line it came from.

- Category: Infrastructure
- Parent: Tooling (`tooling`)

#### Responsibilities

- Read one Markdown file and the project's import map (specs/<project>/import-map.jsonc with "format": "register"), which declares the entity kinds, the table rules (header cells, optional heading scope, the id column or id prefix, a property per column, reference columns), component categories and aliases, and which identifier patterns count as mentions
- Hold every line: headings become sections whose bodies keep prose verbatim, and each imported table row and table header is replaced in its section body by one {{entity:<id>}} marker line; write nothing unless the file rebuilds line for line with each marker expanded to the lines it came from
- Make every row entity render back to its cells: a row rendered from its properties must give the same cells as the source row, or the import fails naming the entity
- Give every imported entity a source property (path:line in the source repository) and, when the row carries an identifier, a ref property with the identifier as written; identifiers and citations named in a row become its mentions (references to imported entities) and citations (as written)
- Record what it recognised but could not map (a row whose cell count differs from its header, an unresolved mention, a duplicate identifier, a reference column naming no entity) as losses with counts and examples, printed and written into the generated specification's system notes
- Merge the draft fragments the map lists ("drafts"): authored entities that are not from the Markdown, each given origin "draft" and the file and line of its declaration as source, citing in basis the imported entities it answers; drafts never change the Markdown the sections render

#### Relationships out

- Reads → Markdown specification: Reads the Markdown file and the repository's git commit; it never writes there.
- Data flow → Specification file: The generated text of the project's specification file travels to the file, deterministically, with the losses recorded in its system notes.
- Writes → Specification file: Writes the project's specification file directly with node:fs, bypassing the transaction system.
- Depends on → jsonc-parser: Reads the import map and re-reads the generated text with the library.
- Calls → Markdown importer: Reuses the Markdown importer's text helpers, loss collection, coverage comparison and git commit reader.
- Calls → File system: Reads the Markdown file and the import map, and writes or compares the generated file, with node:fs.

#### Relationships in

- Data flow → Markdown specification: The headings, prose and register tables of the Markdown file travel to the importer, one way.
- Calls → Test suites: Core tests exercise the register importer on a fixture and analyze its output.

#### Known unknowns

- It writes the project's specification file directly with node:fs, not through the workspace service or the transaction system, like the Markdown importer; once a map says "authority": "jsonc" it refuses to import over that file (only --out writes elsewhere), so edits made in Exegra are not overwritten.
- It does not analyze or validate what it writes; that the output analyzes without errors is checked by the tests and by exegra validate.

#### Implementation

- Status: manual
- Modules: `tools/import-register.js`
- Notes: Run by hand when the Markdown file changes; one way, as the Markdown importer.

### Integrity rules

Declarative consistency rules over a whole specification (the built-in integrityRule kind), evaluated on every edit with counterexamples, enforced by the transaction system as a ratchet, and proved or refuted in Lean with kernel-checked proofs.

- Category: Logical module
- Parent: Semantic core (`semantic-core`)

#### Responsibilities

- Parse a rule of the rule language: forall and exists over the entities of some kinds, all entities, or the values of a term, with an optional where filter; property access that follows references through lists; kindof; ==, !=, in, not in, nonempty; !, &&, || and =>; string, number and boolean literals and literal sets. No recursion and no arithmetic, so evaluation is total
- Check a rule statically: every variable bound, every kind declared, every property declared on some kind; an invalid rule is a validation error
- Evaluate every rule of a model once (memoized per model): holds with the number of instances checked under its leading universal quantifiers, or violated with every counterexample as variable bindings with entity ids and lines; a rule whose quantifier ranges over nothing is reported vacuous
- Report each violation as a diagnostic of the rule severity at the first entity it names (integrity.violated), left out of the blocking error count
- Tell the transaction system which violations of error rules a transaction adds (the ratchet): a violation is identified by its rule and its bindings
- Export a rule to Lean: only the entities it can reach and the properties it reads, every value interned to a natural number, the entities as a balanced search tree; write formal/generated/integrity/<rule>.lean with holds (proof by reflection) or one refutation per witness, each by decide +kernel
- Run exegra prove-integrity: the Lean checker (exegra-lean integrity) must agree with the JavaScript evaluator on the verdict and every counterexample, Lean must accept the file, and every theorem may depend on the standard axioms only; otherwise the rule is incomplete

#### Relationships out

- Calls → Proof export: prove-integrity uses the Lake runner of exegra prove (lakeAvailable, the exegra-lean binary).
- Depends on → Formal semantics (Lean 4): Rules are proved in the formal/ Lean project, built with it.

#### Relationships in

- Calls → Validator: Reports invalid rules, vacuous rules and every current violation as diagnostics.
- Calls → Transaction system: Project.apply refuses a transaction that adds a violation of an error rule (the ratchet).
- Calls → Agent command line: The integrity and prove-integrity commands.

#### Known unknowns

- Property access reads top-level properties of entities only: a nested object property such as implementation.status or evaluate.method cannot be addressed (follow-up of WK-396).
- Entity ids written as literals in a rule are not references: a rename does not rewrite them and a delete does not see them (follow-up of WK-396).
- Undo, redo and reload are not checked by the ratchet: they restore or adopt text that was valid before, and may bring back a violation.
- The Lean facts are exported by JavaScript: that they are the specification is checked differentially (exegra-lean integrity against the evaluator), not proved.

#### Implementation

- Status: manual
- Modules: `src/core/integrity.js`, `src/core/integrity-export.js`, `tools/prove-integrity.js`, `formal/Exegra/Integrity.lean`
- Notes: formal/Exegra/Integrity.lean: Facts (a search tree), Term, Formula, Sat (the meaning), eval and eval_iff, refutes and refutes_sound, Facts.find_complete, cex and the exegra-lean integrity protocol; axioms pinned with #guard_msgs. The commands are exegra integrity and exegra prove-integrity (cli/commands.js).

## Contracts

### Apply a transaction

Project.apply: the single entry through which a project's specification or layout changes (UI, source editor, agent command line). Defined by src/core/project.js and src/core/operations.js.

#### Inputs

- operations (Operation | Operation[]): Typed operations: CreateEntity, DeleteEntity, RenameEntity, SetProperty, CreateRelationship, DeleteRelationship, MovePresentationNode, AddClaim, ModifyClaim, AddState, AddTransition, ReplaceSource, ReplaceLayout.
- label (string): Optional history label.
- origin (string): Optional origin of the change (ui by default, cli, undo, redo, external).
- expectRevision / expectHash (number / string): Optional optimistic concurrency guards against the project's revision or semantic hash.

#### Outputs

- result (TransactionResult): ok, revision after the call, semantic hash, affected entity ids, semanticChanged and the diagnostics of the resulting (or rejected) state; on failure also code and message.
- commit event ({type: 'commit', result, entry}): Delivered synchronously to every subscriber after a successful commit; the history entry says whether spec and layout changed.

#### Preconditions

- The operation list is not empty and every operation names a known type
- When expectRevision or expectHash is given, it equals the project's current revision or semantic hash
- A current model exists unless every operation is ReplaceSource or ReplaceLayout
- Each operation's own preconditions hold (the entity exists and has the right kind, new ids match the id pattern and are unused, parameters have the right shape)

#### Postconditions

- Atomicity: when the result is not ok, the specification text, layout text, model, revision, history and undo stacks are exactly as before
- The resulting specification, if the specification text was edited, has no validation errors; a transaction whose result would have errors is rejected
- On success the revision has increased by exactly one, a new immutable model snapshot derived from the new text exists and the undo stack gained one entry (the redo stack is cleared)
- Presentation operations (MovePresentationNode, ReplaceLayout) never change the specification text or the semantic hash
- Existing comments and formatting outside the edited ranges are preserved

#### Errors

- op.empty: The transaction has no operation.
- op.unknown: An operation has an unknown type.
- revision.stale: expectRevision or expectHash does not match the project.
- model.unavailable: The current source has syntax errors and an operation other than ReplaceSource or ReplaceLayout was submitted.
- validation.failed: The resulting specification would have validation errors, or a replacement source has syntax errors.
- layout.invalid: The resulting layout would be unreadable.
- op.param / op.kind: An operation parameter is missing or has the wrong shape, or an entity kind cannot be created.
- entity.unknown / entity.kind: An id names no entity, or an entity of the wrong kind.
- id.format / id.duplicate: A new id breaks the id pattern or is already used.
- delete.system / delete.referenced: The system entity cannot be deleted; an entity that others refer to is deleted without cascade.
- edit.syntax / edit.not-array: A text edit would leave the specification syntactically invalid, or targets something that is not an array.

#### Obligations

- Callers must show the rejection and its diagnostics to the user or agent; a rejected transaction is never retried implicitly.

### Write a project file

Writing spec.jsonc or layout.jsonc of a project: persistence client, POST /__exegra/write of the development-server plugin, and the workspace service's write function in tools/workspace.js.

#### Inputs

- name (string): Project name matching ^[a-z0-9][a-z0-9_-]{0,63}$.
- file ('spec' | 'layout'): Which project file.
- text (string): Complete new file text, at most 16 MB.
- baseHash (string | null): sha-256 hash of the file text the caller last read or wrote; null means the caller expects the file to be absent.
- meta ({label, origin}): Optional journal annotations.

#### Outputs

- success ({ok: true, hash}): The hash of the text now on disk.
- conflict ({ok: false, conflict: true, current: {text, hash}}): The file's current content, returned instead of writing; HTTP status 409.
- failure ({ok: false, error}): Any other refusal or failure.

#### Preconditions

- The project name is valid and the target path stays inside the project directory
- The file is spec or layout and the text is a string within the size limit
- Over HTTP: the Host and any Origin are loopback and the x-exegra-client header is present

#### Postconditions

- Optimistic concurrency: the file is replaced only if the sha-256 of its current text equals baseHash (absent equals null); otherwise it is left untouched and the conflict result carries its current content
- Replacement writes a temporary sibling file and renames it over the target; writes of one project are serialized
- One line is appended to .history/journal.jsonl for every successful write

#### Errors

- conflict: The file on disk differs from the base hash.
- name.invalid / path.unsafe: The project name is invalid or the path escapes the project.
- file.unknown / input.invalid / too-large: The file is not spec or layout, an input has the wrong type, or the text exceeds 16 MB.
- host.forbidden / origin.forbidden / client.header: The request is not from a loopback host or origin, or lacks the custom header (HTTP 403).

#### Obligations

- A client that receives a conflict must not overwrite silently: the session keeps the conflict until the user chooses to reload from disk or overwrite disk.

### Project a model into a scene

project(model, viewId, ctx) in src/core/projections.js, followed by layoutScene(scene, pinned, {method, aspect}) or chooseLayout(scene, pinned, {aspect}) in src/core/layout.js.

#### Inputs

- model (Model): The committed model snapshot.
- viewId (string): A declared view, or the id of an implicit view; an unknown id falls back to the first view.
- ctx (ProjectionContext): Collapsed and hidden sets, isolated subsystem, focused claim and scenario, the focused entity (for the references projection), claim results, simulation trace and step.
- layout options ({method?: string, aspect?: number}): The layout method (layered, layered-down, packed, radial or auto) and the target width-to-depth ratio of the view; defaults are layered and 1.6.
- pinned (Record<sceneNodeId, [x, z]>): Absolute positions of leaf nodes from the layout file.

#### Outputs

- scene (SceneModel): Nodes, edges, legend and notes.
- placement (Placement): A rectangle on the ground plane for every node; chooseLayout also returns the method it chose and the score of every method.

#### Postconditions

- Every node and every edge of the scene is backed by an entity of the model (it carries that entity's id)
- Pure and deterministic: the same inputs give the same scene and placement, and the model is not changed
- Position carries no meaning: containment and relationships do

#### Obligations

- The renderer draws only what a scene and a placement contain and reads nothing from the model.

### Evaluate claims

evaluateClaims, evaluateClaim and checkTrace in src/core/claims.js.

#### Inputs

- model (Model): The model whose claims are evaluated.
- recorded (Recorded | null): Recorded execution results of evidence, keyed by evidence id.

#### Outputs

- results (ClaimResult[]): One result per claim in declaration order: status, evaluator, semantic hash, scope, explanation, assumptions, involved entities, counterexample and evidence.

#### Postconditions

- A status is verified only when an evaluator checked the claim on the model; a selector that selects nothing is inconclusive, not verified
- A claim whose method is not registered is not evaluated
- Trace-based statuses state that only the listed scenarios' traces were checked
- Evidence can only make a model-evaluated claim worse (a recorded fail or contradicting evidence turns verified into violated), never better
- An external-evidence claim is supported only by a recorded passing test or by non-test evidence, and says whether Exegra executed anything
- Deterministic: no clock, randomness or I/O

#### Errors

- unknown claim: evaluateClaim is called with an id that is not a claim; it throws.
- evaluator failure: An exception while evaluating a claim becomes an inconclusive result rather than aborting the evaluation.

### Engine input, format version 2

Planned (WG-4664, WG-4715). The engine input {format: "exegra-sim-input", version: 2} that simulationInput derives for a specification using resources, workloads, links, instances, timers or seeded randomness. Every version-1 field keeps its meaning with times as integers of the base unit. Normative definition: docs/simulation.md, "Planned: resources, workloads and performance", "Engine input and trace format version 2".

#### Inputs

- version (2): Version-1 inputs are still run by the version-1 semantics; any other value is refused.
- time ({unit: "tick" | "s" | "ms" | "us" | "ns", perSecond: null | 1 | 1000 | 1000000 | 1000000000}): Base unit; times and durations are integers in [0, 2^53). Unit tick allows no rate or bandwidth.
- scenario.seed (decimal string | null): Unsigned 64-bit seed without sign or leading zeros; required when any element draws; not needed when the only random sites are choice values.
- scenario.stepLimit (integer in [1, 2^53)): maxSteps of the specification.
- scenario.horizon / warmup / stopAt (integer | null): Horizon required with workloads; warmup < horizon <= stopAt.
- scenario.output ("trace" | "metrics"): Full trace, or metrics and final configuration only.
- scenario.steps[].target ({behavior, instance}): Optional addressee of an input step.
- behaviors[].instances ({count: integer} | {key: string, max: integer}): Counted or keyed instances; keyed machine keys keep the canonical JSON of the key, quotes included.
- transitions[].effects (Effect[]): Adds emit with after as integer or distribution, target "reply", via, size and fanout; use, acquire, release with class; timer, cancel; set with {sample: dist}.
- routes ({event, behavior, by: "key" | "round-robin" | "random" | "any" | "least-busy", field?, resource?}[]): Instance routing decided when the entry is created; down instances are skipped except by key; any is enumerated by the explorer.
- resources ({id, kind, capacity, discipline: "fifo" | "priority", queueBound, overflow: "refuse" | "drop" | "shed-oldest", demandFactor: [n, num, den][] | {usl: {alpha: [num, den], beta: [num, den]}} | null, classes: {id, priority, reserved, limit, queueBound, maxWait}[]}[]): Resources with capacity, request classes, queue rules and load-dependent demand (a step table whose last row holds beyond it, or USL parameters evaluated exactly at each grant).
- links ({id, from, to, latency: Dist | null, bandwidth: integer | null, queueBound: integer | null, ordered: boolean, fanout: boolean}[]): Bytes per second, a latency distribution, ordering and per-receiver fan-out queues.
- workloads ({id, kind: "open" | "closed" | "population", ...}[]): Open: event, process, phases, repeat, batch, clients {count, pick, addresses}, legitimate, maxArrivals, payload. Closed: event, population, think, start, reply, timeout, payload, legitimate. Population: behavior, count, start, clients, legitimate. Phases: from < until, sorted, non-overlapping; rates count instants.
- unitExponential ([u, x][]): The pinned unit-mean exponential quantile table at scale 2^-64 on the standard grid (x below 2^72), present when a workload is Poisson.
- requests ({id, start: {event, workload?}, key, ends: {event, outcome: "ok" | "refused" | "timeout" | "error"}[]}[]): Request classes measured by the metrics.
- meters ({id, of, measure: "count" | "rate" | "ratio" | "quantile", window, q?}[]): Windowed measurements readable in expressions.
- prices ({id, counts, price: {num, den}, currency}[]): Exact rational prices per counted unit (a delivery, an ended request, a byte, a resource unit held for one second, an instance up for one second).
- metrics ({quantiles: string[], series?: {bucket}}): Quantiles as exact decimals (default 0.5, 0.9, 0.99) and an optional series bucket dividing horizon - warmup.
- faults[] (Fault): Optional window {at, until} (not on crash-instance); adds scale-demand, set-capacity, set-class-limit, collapse-classes, replace-demand and crash-instance {behavior, instance, at, restartAfter?, notify?}.
- Dist ({kind: "fixed", value} | {kind: "uniform", lo, hi} | {kind: "table", points: [u, x][]} | {kind: "choice", values}): Integer distributions; continuous ones are lowered to tables with the pinned quantile tables and 96-bit fixed-point exp and ln.

#### Outputs

- trace (Trace (version 2)): See contract trace-v2.

#### Preconditions

- The input was derived from a validated specification, or is a generated input of the version-2 generator
- Every integer is within its bound (docs/simulation.md, Integers and bounds; distribution tables below 2^53, unitExponential below 2^72); a specification duration that is not a whole number of base units is a validation error, never rounded
- No reserved name is used, ids of behaviors, resources, meters, links and workloads are distinct, and every reference resolves
- Phases are valid: from < until, sorted, non-overlapping, and repeat at least the last until
- Reserved units sum to at most capacity, each class's reserved units are at most its limit, and every request can be granted, for every fault mask the scenario admits
- A keyed behavior's max is at least the sum of the counts of the populations on it
- A seed is present when any element draws

#### Postconditions

- Two calls of simulationInput on the same model give identical documents
- A specification that uses no format-2 construct still derives a version-1 input, unchanged

#### Errors

- refusal: In order after the version-1 refusals: unknown time unit; Field "<path>" must be an integer in [<lo>, <hi>].; a malformed seed; a reserved name; an unknown id; a malformed table; a Poisson phase whose mean interarrival is below 100 base units; a rate or bandwidth under unit tick; reserved units above capacity or above a class limit, or a request that can never be granted; a window on crash-instance; a population larger than its behavior's max; Input samples "<stream>" but declares no seed.; via together with after; workloads without a horizon, warmup >= horizon or stopAt < horizon.

### Trace, format version 2

Planned (WG-4664, WG-4715). The trace an engine returns for a version-2 input: the version-1 trace with integer times, instances, resource and link state, draws and metrics. A version-1 input still returns a version-1 trace. Normative definition: docs/simulation.md, "Planned: resources, workloads and performance".

#### Inputs

- input (engine-input-v2): The engine input.

#### Outputs

- version, timeUnit, seed (2, string, decimal string | null): Copied from the input.
- configuration ({time, machines, pending, resources, links, timers, workloads, meters, routeCounters, streams, down, incarnations}): Machines keyed <behavior> for a single undeclared instance, else <behavior>#<index or canonical JSON key>; holdings per instance and class; timers by stable id; draw counters per stream; pending entries carry scheduledAt and, when addressed to an instance, its incarnation.
- steps[].kind ("deliver" | "drop" | "delay" | "service-done" | "wait-timeout" | "link-done" | "fault-edge" | "client-timeout"): Internal entries are steps of their own and count against the step limit.
- steps[].event ({id, payload, seq, source, scheduledAt, target?, from?, routes?, timer?, incarnation?}): Sources add arrival, timer, resource, link and fault-edge kinds.
- steps[].fired[].instance / ignored[].instance (number | string): The instance the transition ran on; ignored reason adds no-instance.
- steps[].resources ({resource, class, request, action, at, waited?, served?, reason?}[]): enqueued, granted, completed, released, refused, shed, dropped, timed-out, in the order they happened.
- steps[].draws ({stream, index, value}[]): Every random draw of the step in order (for an arrival instant: arrival, batch, then client and payload per entry); value as a decimal string.
- steps[].faults[] ({fault, effect}[]): Adds effects scaled, capacity, limit, collapsed, replaced, crashed, stale and restarted.
- outcome, truncated ("quiescent" | "step-limit" | "error" | "stopped", boolean): A truncated run never satisfies a metric claim.
- metrics (Metrics): Integer measured outputs over [warmup, horizon), from the request lifecycle of docs/simulation.md: requests start when their start entry is first taken as head, a lost start ends as error, only ok requests are finite samples, and counts of unkeyed, duplicate and late ends are reported; nearest-rank percentiles and optional series.
- initialDraws ({stream, index, value}[]): Draws made at the start of the run, in order.

#### Preconditions

- The input is a valid version-2 engine input

#### Postconditions

- Deterministic: the same input, seed and faults give deep-equal traces and metrics
- Every number in the trace other than variable and payload values is an integer
- Held units stay within class limits and capacity, and waiting requests within their bounds, at every settled step (a mid-run capacity cut keeps held units until released)
- The lift of a version-1 input that meets the side conditions of lift_agrees gives this trace minus the version-2 fields equal to the version-1 trace
- With output metrics, the metrics equal those computed from the full trace of the same input

#### Errors

- failed step: Version-1 failures, plus: Value <what> exceeds 2^53.; Value demand scale of "<r>" exceeds 2^32.; Reference "<path>" is ambiguous: "<behavior>" has <n> instances.; Aggregate "<path>" needs numbers, got <type>.; Behavior "<b>" would exceed <M> instances.; Route of "<event>" to "<behavior>" needs payload field "<field>".; Instance "<key>" releases <n> units of "<r>" class "<c>" but holds <m>.; Effect replies to "<event>", which has no requester.; Size of emit "<event>" must be an integer in [0, 2^40), got <value>.

## Scenarios

### A valid visual edit

A valid edit made visually: it is submitted, validated and committed (revision 2), then the projection is refreshed and shown by the renderer, inspector and source editor, and only then the file is written, asynchronously one tick later. Real order: refresh at commit, write afterwards. Ends quiescent with every representation at revision 2 and the file persisted.

- Behaviors: Interaction layer: submit an edit and show its outcome, Source editor: apply a draft and stay in sync, Transaction system: check, validate, commit or reject, Parser: derive the candidate model, Validator: judge the candidate model, Session: refresh on commit, then save asynchronously, Projection: derive the scene of the committed revision, Renderer: draw the refreshed scene, Inspector: refresh from the committed model, File service: replace the file or report a conflict

#### Steps

| At | Event | Payload | Note |
| --- | --- | --- | --- |
| 0 | Edit requested | - | An inspector property change, a dragged node or a dialog submission. |

### A valid source edit

The same pipeline entered from the source editor as a ReplaceSource operation. The refresh and the asynchronous write follow the commit in the same order as for a visual edit.

- Behaviors: Interaction layer: submit an edit and show its outcome, Source editor: apply a draft and stay in sync, Transaction system: check, validate, commit or reject, Parser: derive the candidate model, Validator: judge the candidate model, Session: refresh on commit, then save asynchronously, Projection: derive the scene of the committed revision, Renderer: draw the refreshed scene, Inspector: refresh from the committed model, File service: replace the file or report a conflict

#### Steps

| At | Event | Payload | Note |
| --- | --- | --- | --- |
| 0 | Source apply requested | - | The user applies a valid draft. |

### An edit that fails validation

The operation fails validation: the transaction is rejected, nothing commits, nothing refreshes and nothing is written; the interaction layer shows the rejection.

- Behaviors: Interaction layer: submit an edit and show its outcome, Source editor: apply a draft and stay in sync, Transaction system: check, validate, commit or reject, Parser: derive the candidate model, Validator: judge the candidate model, Session: refresh on commit, then save asynchronously, Projection: derive the scene of the committed revision, Renderer: draw the refreshed scene, Inspector: refresh from the committed model, File service: replace the file or report a conflict

#### Steps

| At | Event | Payload | Note |
| --- | --- | --- | --- |
| 0 | Edit requested | - | An edit whose result would have validation errors. |

#### Active faults

- Candidate fails validation (`validation-fails`)

### A valid edit whose write conflicts with the disk

The edit commits and every view shows revision 2, but the file on disk changed since it was read: the write reports a conflict, the file is not overwritten and the session flags the conflict.

- Behaviors: Interaction layer: submit an edit and show its outcome, Source editor: apply a draft and stay in sync, Transaction system: check, validate, commit or reject, Parser: derive the candidate model, Validator: judge the candidate model, Session: refresh on commit, then save asynchronously, Projection: derive the scene of the committed revision, Renderer: draw the refreshed scene, Inspector: refresh from the committed model, File service: replace the file or report a conflict

#### Steps

| At | Event | Payload | Note |
| --- | --- | --- | --- |
| 0 | Edit requested | - | A valid edit while the file on disk has changed. |

#### Active faults

- File changed on disk since it was read (`disk-changed-externally`)

### A write with a stale base hash is refused and retried

Contract events between the persistence client and the development server's write endpoint (contract write-file): the first request carries a stale base hash and is refused with a conflict; the client retries with the current hash and the write is accepted. The trace reads as a request log: a request, a refused write and a retry.

- Behaviors: Persistence client: write a file, retry after a conflict, Development server: accept a write or refuse it as a conflict

#### Steps

| At | Event | Payload | Note |
| --- | --- | --- | --- |
| 0 | Write intended | - | The session writes the committed text; the client's base hash is out of date. |

## Assumptions

- `machines-abstract-the-code`: The scenario state machines in this file faithfully abstract the code they describe: session.apply, Project.apply and its commit, the session's onCommit and flush, the renderer, inspector and source editor refresh and the workspace write. Rationale: The correspondence between the machines and the code is maintained by hand and is not checked or generated. A behavioral claim here is true of the machines; it is true of Exegra only to the extent that this assumption holds.
- `views-derive-from-committed-model`: Every representation (scene, inspector, source editor) derives its content from the committed model snapshot and from interaction state, and from nothing else. Rationale: The equivalence claims compare the revision each view shows with the revision of the transaction system. They say nothing about a view that kept private state of the specification; the session and the panels are written not to, but that is not checked.
- `relationships-match-imports`: The relationships declared in this file match the real imports and calls of the code. Rationale: They are maintained by hand. The traceability check compares only the module paths that components declare with the files on disk, so a new import that is not declared here would not be noticed by any structural claim.
- `tests-exercise-shipped-modules`: The core tests import and run the same modules under src/core and tools that the application and the agent command line run. Rationale: Test evidence supports a claim about the shipped code only if the test exercises the shipped code and not a copy.
- `browser-tests-run-real-application`: The browser tests drive the real application served by the Vite development server, against scratch copies of this specification and of the multiplayer test fixture (and, read-only, a project linked locally), in the locally installed Chrome. Rationale: They show behaviour in one browser on one machine; other browsers are not exercised.
- `recorded-results-reflect-current-code`: A recorded result of a test in evidence/results.json was produced by the code and the specification as they are now. Rationale: Recorded results carry an outcome and a timestamp but no hash of the code or the model; staleness is not detected.
- `filesystem-honours-atomic-rename`: Renaming a temporary file over the target replaces the target atomically on the file system holding the project. Rationale: The workspace service relies on it for atomic replacement. On Windows it retries a blocked rename and finally writes in place, which is not atomic.
- `single-workstation`: The browser, the development server and the project files run on one developer workstation: one host, one clock, loopback between browser and server, one local disk. Rationale: This is how Exegra is run today (npm run dev). It says nothing about a shared or hosted deployment.
- `workstation-rates-assumed`: The rates and durations of the workstation failure modes are the author's estimates of ordinary development use, not measurements. Rationale: No telemetry exists for the development server or the browser session. A recorded measurement would replace these values; until then they only order the modes by plausibility.
- `one-fault-at-a-time`: On a developer workstation at most one of the listed failures is in progress at a time; two independent failures overlapping within one save is not considered. Rationale: A single user drives one session; overlapping faults are rare enough to leave out of the fault model, and the model says so.
- `seeded-streams-independent`: Draws from distinct SplitMix64 streams (distinct seeds, or distinct stream names under one seed) behave as independent uniform 64-bit values for the purposes of the simulator. Rationale: Metric claims treat runs with distinct seeds as independent and identically distributed (the exact binomial test of docs/simulation.md). This rests on the statistical quality of SplitMix64 (it passes BigCrush) and of the FNV-1a and mix64 derivation of stream keys, which is tested, not proved.
